## Triage

**One root cause covers 5 and 13.** `HudWindow` set its root to `MOUSE_FILTER_PASS` on the
reasoning that it "must not steal clicks from its own children". That is not what PASS does:
PASS delivers the event to the control *and* keeps propagating it, so it reaches
`World3D._unhandled_input`, which walks the character. STOP is what consumes it, and it does
not steal from children -- Godot hit-tests the deepest control first, so a Button inside the
window still gets its click. The same propagation sends an unconsumed mouse wheel to the
camera zoom, which is 13.

Groups, for the order to work in:

- **input routing** (5, 13) -- one fix.
- **items** (7, 9) and the windows around them (8, 10, 11, 3, 4).
- **rendering** (6, 14, 15, 16) -- alpha/material work, needs the render box and a
  measurement each, not a screenshot.
- **features** (17, 18) -- new work, authored-data driven.
- **combat** (1, 2) -- 2 is the attack-distance item already in `docs/TODO.md`.

## Item 14 (hair as a solid block), measured 2026-09-20

Every link in the cutout chain checks out, so the report is **not** explained by anything in it:

1. `chinaman_fighter.bmt`'s hair layer carries flags **`0x341`** -- bit 0 set, the alpha-layer
   flag -- against the body layer's `0x340`.
2. `object_loader.gd` reads that (`LAYER_FLAG_MASK` 0x40 is set, so the word is trusted;
   `LAYER_FLAG_ALPHA` 0x1 is set), so `needs_cutout` is true.
3. The hair mesh names its material `chinaman_hair`, which matches the layer name exactly, so
   `_find_layer_by_name` selects the right layer rather than falling back to index 0.
4. The texture survives decoding with its mask intact: DXT1, **6.52 % non-opaque texels**.
5. `_build_foliage_material` is what gets applied, and the shader scissors on full-resolution
   alpha at 0.5.

So either the report predates a fix, or the player's own dressed body takes a different path
from the one measured here (the measurement used the undressed `chinaman_fighter` material).
**The render was run** (dressed China-man, the grounded newbie kit, Jangan spawn, hardware GL)
and it **reproduces**: the hair draws as a flat dark slab with a hard outline.

But the same run measured something that changes the question. `SRREVAMP_QA_MATS` reports only
layers drawn WITHOUT a cutout, and **no hair layer appears in its output** -- so in a real
dressed run the hair does take the cutout path, with the scissor shader applied. The mechanism
is not missing.

What the run did surface is in the armour:

	QA MAT: heavy_01_ba (heavy_01_ba.ddj, DXT3) is  99.7% non-opaque, flags 0x0140, no cutout
	QA MAT: heavy_01_la (heavy_01_la.ddj, DXT3) is 100.0% non-opaque, flags 0x0140, no cutout
	QA MAT: heavy_01_fa (heavy_01_fa.ddj, DXT3) is  99.3% non-opaque, flags 0x0140, no cutout
	QA MAT: sword1_2_3 (sword1_2_3.ddj, DXT3) is    97.7% non-opaque, flags 0x0340, no cutout

Every worn piece is essentially all non-opaque by alpha VALUE while its flag word says bit 0
clear. That is `BMT_FORMAT.md`'s `blade_14` case again -- graded shading rather than a cutout
mask -- now in the armour family, and it is a standing warning for **item 6**: anything that
"fixes" see-through clothes by honouring that alpha as transparency would make the clothes
nearly invisible. The flag is what draws the line, and it says solid.

So for the hair the question is no longer "is the cutout applied" but "what is the cutout
supposed to look like". DXT1 alpha is 1-bit and only 6.52 % of the texture's texels are
transparent. Whether a hard scissor on a mostly-opaque 1-bit mask is what the original does, or
whether the block is simply what this low-poly hair shell looks like when it is correct, is
**not established** -- and is not something a picture can settle.

One more thing the run turned up that nobody has explained: `CJ_luxu_winlight` carries flags
**`0x0348`** -- bit 3 set on top of the usual `0x40`, with bit 0 clear. A flag bit in the wild
that neither known bit covers.

## Item 6 (see-through clothes) diagnosed: it is not transparency at all

The render made it concrete -- the bare chest shows through the cuirass -- and the cause is
geometry, not alpha.

**srrevamp draws the naked body AND the armour.** `_build_assembled_character` assembles the
whole character `.bsr` (for a China man: `man_arm_lower`, `man_arm_upper`, `man_calf`,
`man_pelvis`, `man_thigh`, `man_torso_lower`, `man_torso_upper`, plus face and hair) and then
calls `SkinnedBsrAssembler.attach_item_from_archive` per worn item, which only ever ADDS
meshes. Nothing is ever hidden. The skin and the cuirass end up as near-coincident surfaces and
the skin wins wherever it is nearer -- which is what "his nips are coming out" is.

So the armour alpha finding above is a red herring for this item: honouring that alpha would
make it worse, not better.

**What the engine does instead** (`sro_client.exe`, `CObjCharacter.cpp`, found through the
round-279 translation-unit map):

- `CObjCharacter::SetDefaultWear(nDefaultWearNum, nEquipSlot)` (`0x00a5cca0`) asserts
  `(nEquipSlot >= 0) && (nEquipSlot < EQUIP_VISUAL_COUNT)` against 0..8 and
  `(nDefaultWearNum >= 0) && (nDefaultWearNum < DEFAULT_WEAR_NUM)` against 0..1. So
  **`EQUIP_VISUAL_COUNT` is 9** -- the same nine slots `EquipmentNet.SLOT_HELM..SLOT_EXTRA`
  already uses -- and **`DEFAULT_WEAR_NUM` is 2**: every visual slot carries two default parts.
- `CObjCharacter::BuildDefaultWearTypeID` (`0x00a5c760`) builds those parts as packed item
  **TypeIDs**: base `0x2c`, bits chosen by the gender byte and `WornArmorClass()`, then
  `| 0x1800` for default-wear 0 and `| 0x2000` for default-wear 1. The result is looked up as
  an item row and yields a `pVisualData`.

So a character's visible parts are **per equip slot**, and what is drawn in a slot is either the
worn item or that slot's default wear. The archive agrees: `MAN_ITEM` carries `clothes_00_ba`
and `clothes_00_la` beside the real armour, which is what a default wear looks like.

**What is NOT established**, and so is not being coded: exactly which body meshes a given slot
owns -- that is, what the engine hides when a slot is filled. The mechanism above is read; the
mesh-to-slot mapping is not, and guessing it would put invented geometry rules into the one
system this report is about. The next read is `CObjCharacter::FUN_00a604f0` (asserts
`pVisualData`) and `FUN_00a60a90` (asserts `GetCompoundObj()`), which are where the visual data
becomes the drawn compound object.
