# Server error codes, and the client's name for each

The server refuses an action by returning a 16-bit code — `0x300d` for the wrong
weapon, `0x18fe` for a full container, `0x183e` for an item that cannot be used.
The numbers carry no meaning on their own. The client turns each into a message,
and `UI_SILKMALL::FUN_007b8b40` (10,296 bytes, 643 switch cases) is where.

Regenerate with `client/tools/ghidra/recover_error_codes.py`.

## Why the decompiled client says this is unrecoverable, and is wrong

Every case ends in a call that takes the message name as a wide string, but the
argument arrives in a register and Ghidra drops it:

	case 0x180f:
	  RefData_worldmapguidedata::FUN_0046e3d0();

Reading the dump, the mapping looks data-driven and out of reach — which is what
an earlier pass of this project concluded. In the **disassembly** the string is
sitting right there:

	7b8ca6:  push 0xdc7ea0          <- pointer to a UTF-16 message name
	7b8cab:  lea  ecx,[esp+0x3c]
	7b8caf:  call 0x46e3d0

## The check that makes this trustworthy

`0x183e` resolves here to **`UIIT_MSG_STRGERR_CANNOT_BE_USED`**. This project had
already recovered `0x183e` from the *other binary*: `CUsedItemLimit::FUN_004a05b0`
in the server returns it when an item is refused for having reached its use
limit. A server-side item-use limiter and a client-side "cannot be used" agree
without either being consulted about the other.

## A second check, from the other direction

`0x18fe` resolves to **`UIIT_STT_STORAGE_EXPANSION_USE_ERORR`** (the game's own
typo). This project recovered `0x18fe` from the server two days of ticks earlier,
as the refusal `CGObjPC::ExpandInventory` returns on its `kind == 3` path — and
explicitly declined to name what that container was. The client names it: storage
expansion. Two binaries, again agreeing unprompted.

## A third check, on the weapon gate itself

`0x300d` resolves to **`UIIT_SKILL_USE_FAIL_WRONGWEAPON`**. This project named
`FUN_0058d480` "the weapon gate" from the *server* alone, on the strength of that
being the code it returns when the equipped weapon matches neither of a skill's
`ReqCastWeapon` bytes. The client confirms the whole reading, independently.

Three of its neighbours come with it, and they reach further than the gate:

| code | name | where the server returns it |
|---|---|---|
| `0x3003` | `UIIT_SKILL_USE_FAIL_NOTLEARN` | — |
| `0x3006` | `UIIT_SKILL_USE_FAIL_WRONGTARGET` | — |
| `0x300d` | `UIIT_SKILL_USE_FAIL_WRONGWEAPON` | `ReqCastWeapon` mismatch |
| `0x300f` | `UIIT_SKILL_USE_FAIL_BROKEN_WEAPON` | when vtable slot `0x5d0` (`58d527`), `0x63c` (`58d556`) or the Value-0 armour scan's `0x640` (`58d5de`) returns 0; the Valued-armour `0x640` call at `58d599` sets no code (round 490) |

That last row **names what three unnamed vtable slots do.**
`docs/protocol/igobj_vtable.md` lists 353, 372, 399 and 400 as unreachable by the
stub harvest, because they have no base-class stub and so leave no string. The
error code supplies the meaning instead: a cast-requirement entry checks that the
required item is present *and serviceable*, and failing the second half is
"broken weapon".

## A code does not always mean one thing

The dispatcher selects a **category** first and only then switches on the code,
so the same 16-bit value can carry different messages in different categories.
An earlier version of this table merged them, which silently invented mappings —
it is why `PARTYERR_UNKNOWN_ERROR` briefly appeared to be returned by a
magic-option function.

Measured: of 614 distinct codes, **605 are unambiguous** and **9 are
category-dependent**. Only the 605 are listed below; the 9 are in
`errcodes_ambiguous.tsv` beside the tool and must not be used to label anything
without knowing the caller's category. They are the low generic ones —
`0x0003` is `PARTYERR_INVALID_TARGET`, `STRGERR_INVALID_TARGET` **or**
`ERR_COMMON_INVALID_TARGET` — which is exactly the set most likely to be
grepped up by accident.

## Coverage

**614 of the dispatcher's 643 cases.** The progression is worth recording because
each jump was a bug in the reader, not new data:

| | codes | what was fixed |
|---|---|---|
| first pass | 95 | — |
| second | 445 | the walker stopped at `jmp` with a push outstanding, dropping every case that uses the shared call tail |
| third | 614 | the walker only knew `sub eax,base`; MSVC normalises the case base with `add eax,<negative>` just as often (`add eax,0xffffcffd` is `eax -= 0x3003`), which is how the entire `0x30xx` family was missing |

The remaining ~29 either `break` without emitting a message, or `goto` into the
middle of another case's block *after* its push, where no string can be
attributed to them.

## The other half: which server function raises each code (round 301)

This page maps a code to the **client's** name for it. The server side -- *which
function returns that number* -- is `docs/protocol/error_emitters.tsv`, swept by
taking each code in the table below and finding its enclosing functions in the
server dump.

| | |
|---|---:|
| codes in the table | 605 |
| appearing anywhere in the server dump | 489 |
| emitted by **exactly one** function | **294** |
| ...whose emitter is already named (the control) | 146 |
| ...whose emitter is still `FUN_` (the yield) | **148** |

**It attributes; it does not name.** Controlling on the 146 whose emitter is
already named, only **58.9 %** share a word with the message. Inspection shows
most of the remainder are right anyway -- `CanBeEquipedAt` raising
`HIGHER_STRENGTH_REQUIRED`, `CheckCanUse` raising `CANT_PETSUM_HIGHLEVEL`,
`OfferItemToPartner` raising `NOT_ENOUGH_OPPONENT_INV_SPACE` -- so 58.9 % is a
floor on a semantic relation rather than a measure of one. The message names the
**refusal**, not the function, and turning 148 of them into names would repeat
the mistake `naming_ceiling.md` records for the one-part log label.

**The measurement needed fixing before it could be believed.** The first pass
scored **11 %**, because the tokeniser split `UIIT_MSG_FLEAMARKET_ERR…` on
underscores but left `CFleaMarket__SellFMarketItem` whole. Splitting CamelCase
took it to 58.9 %. An 11 % result would have discarded a working lever.

**Where the value is: the grouping.** 35 of the unnamed functions raise more than
one code, and several refusals converging on one address say what it does --
`004a9050` raises both `CANNOT_BE_PICKED` refusals, `00617360` the three
currency ones (`NOT_ENOUGH_COIN`, `ARENA_NOT_ENOUGH_COIN`,
`NOT_ENOUGH_SILK_TO_BUY_ITEM`), `00617f70` both `DEALER_DONT_TREAT_*`.

Round 300 is what suggested this: `HGPFULL_NODRINK` is in neither binary, and
grepping the server for its **code** found the one emitter and settled a
three-round question in a single command.

## A blind spot in how this table was built, measured 2026-09-16

The table was harvested by scanning the server disassembly for `mov ax,0xNNNN` /
`mov eax,0xNNNN` — the shape of `return ERRORCODE`. **That misses every code that
never passes through ax/eax.**

`Mastery_LevelUp` (`0x0059c4e0`) is the proof. It raises two codes and assigns
both to a stack local rather than returning them directly:

	uStack_22c = 0x3804;   // the target mastery level exceeds the character's
	uStack_22c = 0x3802;   // not enough skill points for the summed cost

Neither appears in the scan's output.

### The pattern was widened, 2026-09-17

`client/tools/re/errsites.py` is that scan, done properly — every constant
materialisation rather than only `mov ax`:

| | narrow (`mov ax/eax`) | widened |
|---|---:|---:|
| (function, code) pairs | 391 | 924 |
| functions carrying a named refusal | **157** | **362** |

So **205 functions carrying a named refusal were invisible to the narrow
pattern.** The shapes it missed, by yield: `mov WORD PTR [reg],CODE` (an
out-parameter), `mov DWORD PTR [esp+N],CODE` (a stack local — this is
`Mastery_LevelUp`'s shape), `push CODE`, `mov ebx/edi,CODE`, and `cmp ax,CODE`,
which attributes the *handler* of a code as well as its raiser.

The richest thing in the difference was `FUN_0058d8f0`, the skill-use gate, with
seventeen distinct refusals — more than any other function in the binary. It has
its own page now: `docs/protocol/skill_use_gate.md`.

Two traps, both of which produced wrong counts before being fixed:

- **Displacements are not constants.** `mov ecx,DWORD PTR [esp+0x3003]` is a
  stack access, not the weapon-gate refusal. Blanking bracketed expressions
  before scanning drops the function count from 414 to 362 — 52 functions were
  pure noise.
- **Some codes are computed rather than written.** The skill-use gate spells one
  refusal as `(-(ushort)(x != 0) & 0xfff1) + 0x3018`, yielding `0x3018` or
  `0x3009` with neither present as an immediate. No scan over immediates finds
  those, widened or not, and the tool does not claim to.

### What the widened scan did NOT explain: the `0x38xx` family

This section used to assert that the `0x38xx` family's absence "is a property of
the probe, not of the game". **That was wrong**, and it conflated two different
probes — the *server* scan that finds where a code is raised, and the *client*
dispatcher walk that gives it a name.

Measured: **no function in `sro_client.exe` has a `0x38xx` switch case at all.**
The dispatcher is genuinely the only one — checked by counting switch cases on
values ≥ 0x100 across the whole client, where `UI_SILKMALL::FUN_007b8b40` has
**624** and the next-largest has **36** (and that one, like the other four
above twenty, switches on a disjoint range: `0x01xx`–`0x0fxx`, opcodes rather
than error codes). Its families are `0x0c, 0x18, 0x1c, 0x28, 0x2c, 0x30, 0x3c,
0x40, 0x44, 0x48, 0x4c, 0x54, 0x58, 0x64, 0x68, 0x6c, 0x70, 0x78` — and `0x38`
is not among them.

So `0x38xx` codes are raised by the server and have **no message in the client's
error dispatcher**. Mastery refusals must surface through some other path, or
not at all. That is a fact about the game, and naming the family needs a
different source than this one.

The remaining bound on completeness: the narrow scan found 445 distinct codes
≥ 0x100 in ax/eax of which 201 are not in this table. Some of that is
legitimate — a code the client has no message for cannot be named here, and
`0x38xx` is now a proven example of exactly that.


## RETRACTED: "thirteen codes the server refuses with" (round 323, withdrawn round 325)

Round 323 claimed thirteen codes -- `0x1806`, `0x1807`, `0x1811`, `0x181d`,
`0x1c0d`, `0x1c0e`, `0x3c0f`, `0x3c2a`, `0x3c32`, `0x3c33`, `0x4c33`, `0x6006`,
`0x6008` -- are refusals the server sends and the client cannot render. **The
method was unsound and the claim is withdrawn.**

It rested on grepping the decompiled C for `FUN_004e7250(0x...)` and reading the
argument as an error code. `FUN_004e7250` is not a refusal sender. It is a
generic two-field reply helper:

	FUN_004e7250(opcode):            ; opcode arrives in ECX
	    msg = this->slot_0x278(opcode)
	    append two words from the frame
	    this->slot_0x27c(msg)

and the error code is one of the appended words, arriving in a **different**
register. At the very call site that produced `0x1806`, the disassembly reads:

	4f0d1a  mov ecx,0xb034     <- the REPLY OPCODE, the actual argument
	4f0d19  push eax           <- the payload
	4f0d25  call 0x4e7250

Ghidra rendered that call as `FUN_004e7250(0x1806)`, naming a payload value as
the argument. Across call sites it resolves sometimes to the opcode and
sometimes to the payload, so the grep collected a **mixture** -- which the three
impossible values in round 323's own output (`0x3`, `0x5`, `0xb`) should have
flagged at the time and did not.

**What survives.** These values are not valid reply opcodes (replies are
`0xbXXX`), and they sit inside families whose neighbours are named errors, so
they are *plausibly* error codes. That is where the evidence stops. Whether the
server emits them, and whether the client can render them, is **not
established**.

`UIIT_MSG_GUILDERR_PERMISSION_DENIED` (6). The client genuinely shows one string
for all of them, so the name is the *text the player sees*, not a label for the
refusal.

The join in this page is therefore sound in one direction only: a code gives you
its message, but a message does not give you back the code, and for those 157 the
message does not distinguish what actually went wrong. Anything reasoning
backwards from a name -- including any attempt to NAME a function from the codes
it raises -- has to check the code's own uniqueness first.

**One of the fifteen is corroborated from an unrelated reading.** `0x4828` is
what `docs/protocol/jobs.md` records the job-join handler returning for a kind
outside {1,2,3}, read in round 273 from a different function on a different day.
A refusal a player can actually trigger, with no message behind it.

### This table is exactly reproducible (checked, round 323)

`recover_error_codes.py` was re-run against `sro_client.exe` and produced **605
unambiguous codes and 9 category-dependent ones**, matching this page row for
row -- **605 of 605 identical, zero differences**. For a 605-row table recovered
through two jump tables, that is worth having checked rather than assumed.

**A miscount worth recording**, because it looked like a gap: counting `case`
labels in the decompiled switch gives 643, against 605 here, and the 38-odd
difference reads as missing work. It is not. Twenty-three are small values from
a different switch arm, seven are the category-dependent codes this page already
excludes by name, and the rest are labels like `case 0x6415: goto LAB_007b9116;`
which share a block and carry no string of their own -- so the tool correctly
declines to give them a unique name.


## The interaction pair: `0x1c0b` and `0x1c0d` (round 449)

These two are complements, and reading them together is what gives each a
meaning neither has alone.

| code | raised by | when |
|---|---|---|
| `0x1c0b` | `GObjPC_HandleShopMsg_046` (`0x510250`) | an interaction was requested while `chardata+6` (INTERACTMODE) is **already non-zero** |
| `0x1c0d` | `GObjPC::EndInteraction` (`0x5107c0`) | an interaction was ended while **nothing is open** |

`0x1c0b` is raised twice in the open handler, at its two earliest guards, before
any message field is read -- the handler rewinds the cursor
(`msg+0x103c := msg+0x103e`) on both paths precisely because it is abandoning a
read it never made. `0x1c0d` is the close handler's only refusal.

So the pair is "already busy" / "not busy", and **neither has a `case` in the
decompiled client** -- both are in the fifteen listed above that the server
sends and the client cannot render. That remains true; what changed is that the
two are no longer unexplained.


## `0x480f` means "wrong job guild NPC" (round 453)

Listed above only as a code `JobGuild_HandleWithdraw` pushes, with no sense
attached. It is the refusal raised when `CGObjChar::HasAvailableInteraction`
says the target NPC does not offer **your job's** guild interaction, and three
handlers raise it from that same failed check:

	CInstanceCharTrijob::HandleJoinJobGuild   kind byte  -> 0x14 / 0x15 / 0x16
	JobGuild_HandleWithdraw                   the same mapping
	GObjPC_HandleAliasMsg_0e3                 the player's OWN job type

with `0x14`/`0x15`/`0x16` being the Trader, Thief and Hunter guild interaction
ids (`docs/protocol/jobs.md`). It remains one of the codes with no `case` in the
decompiled client, so the client cannot render it — what changed is that its
meaning is now read rather than unknown.
