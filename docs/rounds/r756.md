# Round 756 — a crowd appears at once: arriving bodies drawn as GPU ghosts

The user, walking up to a live crowd of thousands: "when I come up to the crowd one player loads
at a time. They should all pop up at once."

That was rounds 739/748's arrival pump: an arriving body was invisible until it was dressed, and
the dressing ran nearest first under a per-frame time budget that follows the frame
(`HITCH_TARGET_USEC`, 90 ms). At crowd frame rates that is about one body a frame, so a crowd
filled in over 13-15 s.

Labels: **READ** (the retail client's decompile on the box, or our code / Godot 4.2.2's source),
**MEASURED** (the box: RX 7600, RADV NAVI33, Forward+ through `xwl_run.sh`, 1920 x 1080, vsync
off, Middle), **COMPUTED**, **INFERRED**, **OURS**, **OPEN**. Everything is measured with every
feature on, at the defaults.

Base: `9a5732ed` (dev, v0.1.511 plus a lint).

## 1. What retail does (READ)

From `/var/tmp/decomp_client` (with `sro_client.asm`, `vt_client.json` and constants read from
`sro_client.exe`).

**A group spawn creates every character in one call, in one frame.**

- 0x3017 (`FUN_008ac0e0`) writes the type byte and the u16 count into a buffer
  (`FUN_00508fe0`); each 0x3019 (`FUN_008ac170` -> `FUN_00833380`) appends to it. Neither creates
  anything.
- 0x3018 (`FUN_008ac3d0` -> `FUN_008a6d20`) parses the whole buffer: for type 1, a plain loop
  `do { FUN_008a6bd0(stream, 0); } while (--n)`, then clears it (`FUN_008ac340`). No budget, queue
  or deferral.
- `FUN_008a6bd0` -> `IGIDObject::FUN_009c1fa0` -> `FUN_009c1ce0` -> `FUN_00ba36d0` (the entity
  manager's create): the id, the class's CreateObject, the map insert, vslot 7's init and the body
  reader (vslot 0x64), all in that call. Its only refusal is the manager's `+0x3c` flag.
- A single 0x3015 (`FUN_008a6ca0` -> `FUN_008a6bd0(stream, 1)`) is the same synchronous create
  (with vslot 0x68, `FUN_009c2180`, reading the spawn byte).
- The packet pump drains everything that arrived each tick (`MsgStreamBuffer::FUN_00842ff0`:
  dequeue `0x834920`, dispatch `0xba8f70`, free `0x832c60` while `[edi+0x490] != 0`, asm
  0x843273-0x84327a), so a 0x3017..0x3018 run is handled in one tick.

**The model and the equipment meshes are loaded synchronously; only textures load in the
background.**

- The body: CICUser vslot 25 `GlobalDataManager::FUN_009de2f0` -> vslot 0x60 `FUN_009dade0` ->
  `FUN_009c1d10` -> `FUN_009c4ec0(refobj+0x124)` -> `CCObjAnimation::FUN_00a5b4b0` ->
  `FUN_009ef2f0`, which takes a cached instance (`FUN_009ef120`) or builds one
  (`Map::FUN_009fe760` -> `CResourceMgr::vslot_004` 0xbedc40 -> `ResourceMgr::FUN_00bedba0`, cache
  `FUN_00beacc0` or `FUN_00bed8d0`: the file opened and read now, `"ResObj Data Loading Failed
  [%s]"` on failure). `FUN_009c4ec0` then copies the model's bounding box into the object
  (+0xa0..+0xb4), and on a null model loads `res\mob\china\mangnyang.bsr` synchronously instead.
  No placeholder, no loading state. (OPEN: one cache branch calls a callback set at run time,
  `[0x1103d87+0x1c]`; its result is used at once, so INFERRED synchronous.)
- The equipment: vslot 0x40 `FUN_009db940` -> `CCObjCharacter` slot 8 `FUN_00a61c60` ->
  `FUN_00a611e0` -> `FUN_00a60a90` -> `FUN_00a604f0` -> `CObjCharacter::FUN_00a5f4f0`, which loads
  each item's `.bsr` (and its `_l/_r/_f` variants) through ResourceMgr vslot 4 and asserts
  `"pIResItem"` / `"pLoadObjHand"` on the result.
- The only resource thread is the texture loader (`rtloading::FUN_00b8bbc0`,
  `g_pRTTextureLoadingManager`; thread `FUN_00b8bac0` -> `FUN_00b8b5d0`). `CPrimTexture::FUN_00c1d020`
  loads synchronously while `[0x1112fb0+0x1b4]` is set and queues the texture otherwise; the select
  screen and the own-character load set it and put it back (0, INFERRED). So in the world a new
  texture loads in the background, and until it does the mesh is drawn with no texture bound
  (`CObjRendererVS::FUN_00bf3b70` calls SetTexture with no null check, asm 0xbf3c1d-0xbf3c48; READ;
  what that looks like is OPEN).

**It is drawn and clickable the frame it is made.**

- The frame: the message pump, then `CGame::vslot_011` (the packets, then the update), then the
  render (`FUN_00ba4020`). The draw (`FUN_00ba2570`) draws every entity with an id and `+0x40`
  (set by the CIEntity constructor); the base draw `0x9c4aa0` skips only `+0xd4 & 2`, hidden
  (`+0x70 & 1`), no model, or outside the frustum. No "resources ready" test.
- The appear fade starts during the parse (vslot 0x6c, 2.0 s from alpha 0: round 676).
- The pick (`FUN_0078ee20`) walks every CIGIDObject; for a CICUser it needs `+0xbc` (1 from the
  CIObject constructor `FUN_009c4860`, then the last draw's frustum result), no stealth 4, not
  `FUN_009c7580`. It tests the ray against the model's bounding box set at load (`FUN_009c7620` ->
  `FUN_00a5b000`: a sphere reject, then the 12 triangles of the box), nine rays, the nearest hit,
  no distance cap. So a new character can be clicked at once.
- Names: within 300 of the player (round 673, unchanged).

**So retail's crowd appears in one frame, every body fading in together over 2 s**, at the cost of
one long main-thread stall for models it has not loaded (INFERRED from the synchronous loads), with
new textures popping in as the loader thread finishes them.

## 2. The design (OURS unless marked)

A far body needs no node to be drawn: round 747's CrowdGpu draws it from its kind's meshes, the
baked frames of its clip and a per-body texel. Round 756 draws an arriving body that way at once,
before it is built: a **ghost**.

### The recipe (`CharacterAppearance.far_recipe`)

What `build()` would draw for (body, scale byte, items), read off the cached templates without
building a node: each piece is a template's own MeshInstance3D with what `build()` leaves on that
mesh's copy:

- the material: the glow at the item's plus (`EquipGlow.material_for`, as `_apply_glow` puts it);
- the skin: the shared skin's Volume variant for the scale byte (`apply_volume`'s rule; cached by
  skin and byte);
- where it hangs: skinned to the body, or from a body bone through its BoneAttachment3D (the chain
  of transforms under it);
- the body's own pieces the worn items hide are left out: `SkinnedBsrAssembler.hidden_body_nodes`,
  now the rule `apply_body_hides` itself applies;
- the `_r`/`_f` fallbacks and the default wear as `build()` resolves them; Height as its scale.

It is null when a template is still to be made (the body waits, as before) or when `build()` would
grow the skeleton (an item needing a bone the body template lacks: the body is dressed instead).
Recipes are kept per kind.

**Parity (MEASURED):** `client/tools/arrival_bench.gd` builds 300 random kits from the item table
(every Figure, an armour piece a slot of its race and sex, a weapon, a shield half the time, a plus
0-13 on both, a random scale byte) on real archives and compares, for each, the far parts CrowdGpu
reads off the built body (`_parts_of`) with those it reads off the recipe: **293 compared, 0
mismatched** (mesh, twin material, Volume row, centre height, layers, sorting offset), 7 refused by
both (blended parts, round 747's F8). `crowd_ghost_test` holds the same on synthetic templates
(Volume, a hidden piece, a hung rigid item).

### The ghost (`CrowdGpu.add_ghost`)

- A body slot, a clip texel, an instance a part, from the recipe's parts (`_part_for`: the rules
  `_parts_of` reads a built body by, split out of it), keyed by the holder node instead of a
  skeleton. The parts and their twins are worked out once per recipe and light level.
- **The fade (READ: 2.0 s in, 1.5 s out, AppearFade):** a fading ghost's parts draw from groups of
  their own with the blended fade twin of their material (`AppearFade.fade_twin`, with the skin
  added). Their alpha is worked out in the vertex shader per instance, from the clock and the
  fade's start written in `INSTANCE_CUSTOM.w` (`srr_cg_fade`: AppearFade's truncated byte, 255 /
  2.0 s x elapsed in, 255 - 255 / 1.5 s x elapsed out), so one fade twin a material serves every
  fade and no material changes while fades run. When the fade ends the parts move to the shared
  groups; a departing ghost fades out the same way and then leaves. OURS approximation: the
  instances of a fade group are one MultiMesh and are not sorted against each other during those
  2 s (the fade twins write depth, as the near ones do).
  - The first build made a fade cohort a frame with its own twin per material and alpha uniform,
    as AppearFade does for near bodies: about 100-300 material copies a frame while a page
    arrived (MEASURED in the frame split: 0.4 ms of `g_add` a ghost). Per-instance alpha removed
    them.
- **Light:** a ghost is drawn at its materials' own 0.6 at first (at alpha 0, its fade's start),
  and takes the colour CharacterLight reads where it stands over the next frames
  (`_light_ghosts`, 8 ms a frame, nearest first; its level's material copies,
  `ObjectLight.with_object_color`). Reading it (the navigation surface and the ShadowMap under the
  body) was about 0.23 ms a body, a third of a ghost (MEASURED, `g_light`). CharacterLight's own
  visits re-light it as it walks (`CharacterLight.on_value`). OURS: the order (draw, then light).
- **Walking:** a ghost's stand/run swap is a texel write when the loop is baked
  (`_set_ghost_gait`); when it is not, the ghost is dressed and swaps on the full path.
- **Sounds:** its clip sounds are registered with the holder as the key, and the far bodies' 600
  rule (round 747's F2) covers ghosts too (the scan includes them).
- **A clip not baked yet:** the ghost waits (its kind is not asked again until a clip goes up,
  `clip_generation`), and baking runs at 16 ms a frame instead of 4 while one waits.
- **The budget** (`OtherCrowd.GHOST_BUDGET_USEC`, 50 ms, OURS) follows the frame as the dressing's
  does (`note_frame`, aiming at 90 ms with the light pass counted): a 3000-body crowd's own frame
  is 35-45 ms, and 50 ms of ghosts on it made 110-160 ms frames (MEASURED, the first 3000 boot).
- **AABB:** the shared bounds grown by the ghosts of a frame go to the groups once, with their
  instances (they went per body, a call per group each time).

### What the holder gets at once

`_ghost_other` adds what `_dress_other` would add to the holder: the name plate and the click body
over the body's height (the body template's meshes: `build()` hangs no other drawn child on the
skeleton itself, so the height is the same), its circle shadow (`CharacterBlobs`), its clip sounds.
So names (within 300, READ), click and selection work from the frame it appears, as retail's pick
does.

### The dressing follows

- The same pump as before (`_other_builds`), nearest first, after the ghosts in the frame. A body
  nobody sees (its ghost refused: a blended part, an unknown body) goes before every ghost
  (`BuildQueue.pump`'s `later`), and while one waits the dressing keeps round 748's 90 ms aim;
  otherwise every waiting body is drawn and the budget aims the frame at 33 ms
  (`GHOST_HITCH_TARGET_USEC`, OURS), so the background dressing does not hold the crowd's frame
  near the hitch line (at least one body a frame still).
- **The near set** is dressed first among the ghosts (nearest first), a few a frame, not all 16 in
  the arrival frame: 16 dressings (3.5 ms each, MEASURED) on top of the page's ghosts would put
  the arrival frame over 100 ms. A near ghost draws the same pixels as the dressed body (the GPU
  plays the same frames), less its weapon's particles, until then.
- **The hand-over** (`_ghost_handover`): the built skeleton takes the ghost's clip entry (its clip
  and phase) in the same call; it is drawn far from the skeleton at once (the same meshes,
  materials and clip: the same pixels), unless it is within the near set (the last cycle's line),
  still fading (it fades on from where the ghost's fade was: `AppearFade.Fades.start`'s new
  `elapsed`) or not eligible -- then it is posed on the full path at its clip's frame. No second
  plate, click body or circle.
- **Dressed at once** (`_dress_ghost_now`) whenever something needs the skeleton: a one-shot (a
  hit, a cast, sitting down or getting up), an effect or aura, berserk, Detail choosing it as a
  caster, A5 switched off.
- An equipment or plus change draws the ghost again in its new kind once that kind is ready (the
  old look stays meanwhile; a fade-in goes on).
- What a ghost lacks until it is dressed: its weapon's particles (EquipFx hangs them on the
  weapon's item skeleton; retail draws them at every distance, READ round 734) and Detail's
  shadow (a caster is dressed when chosen). At 1000 every body is dressed 13.7 s after the first
  packet; at 3000 the crowd's frame is over 33 ms, so the dressing goes one body a frame and takes
  136 s (MEASURED, below).

### Kinds whose templates are not made yet

Retail loads the model synchronously (section 1): its crowd appears in one frame, after a stall.
This client keeps round 748's worker-thread templates: a body whose kind is not ready stays
invisible, and **every body of a kind appears in the frame its templates are adopted** (the ghost
queue is looked at whole again then). Measured both ways and with more tasks (section 3): the
first of its kind built on the main thread (`OPENSRO_QA_SYNC_TEMPLATES=1`) made the 200-body
arrival slower to show (5.97 s against 4.09) with a 502 ms frame and 19 over 100 ms; 4 or 8 template
tasks at once instead of 2 (`OPENSRO_QA_PREP_RUNNING`) gave no earlier crowd (4.4-5.8 s against 4.2)
and frames of 171-939 ms. So the cap stays 2, and a cold crowd shows kind by kind as its templates
come, each kind whole.

## 5. Open

- **A cold crowd waits for its templates** (about 4 s for the lineup's 52 kinds on two tasks),
  where retail stalls one frame and shows everything. More tasks did not help (section 3); what
  would is cheaper templates (the assembly is 50-400 ms of GDScript a kind, round 748) or the
  native readers on the box.
- **What a ghost lacks until dressed:** its weapon's particles, and at 3000 the dressing takes
  over two minutes (one body a frame). A particle host that does not need the item skeleton
  (EquipFx placing from the recipe and the GPU frame, as `CrowdGpu.item_frame` already does for a
  far body) would let a ghost wear them.
- **The fade groups are unsorted** for their 2 s (section 2): bodies fading together overlap in
  instance order, not depth order.
- The near set is dressed a few a frame after the page's ghosts, not in the arrival frame.
- Retail's texture loader thread draws a new texture's mesh unbound until it loads (READ); what
  that looks like on screen is OPEN, and this client has no equivalent (its textures load with the
  templates).

```
flock /var/tmp/godot-lock/lock /opt/opensro-client-<lane>/tools/crowd_run.sh \
  /opt/opensro-client-<lane> /var/tmp/<lane>/n1000.log 1000 base,move,dest,base
# the walk-up
... crowd_run.sh <dir> <log> 1000 base,move,base OPENSRO_QA_LINEUP_WALKUP=1.5 OPENSRO_QA_LINEUP_SPACING=16,24
# before round 756 in the same tree
... OPENSRO_QA_GHOSTS=0
```

`QA CROWD visible` and `QA CROWD page` are the arrival's lines (`client/tools/README.md`, "An
arrival"); `QA GHOSTS slow pump` and the arrival split's `g_*` timers the ghosts' own time;
`client/tools/arrival_bench.gd` the per-body costs and the recipe parity on real archives.
