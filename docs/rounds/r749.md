# Round 749: C3, moving by destination, as retail does

The user's goal is 10,000 players. Round 737 measured the biggest server lever for it: the client
streamed about 20 positions a second while walking, where retail sends one move request per click
and the server answers one 0xB021 per accepted move (`docs/rounds/r737.md`, "C3 as a spec"; its
review's 10k section). This round builds it, client and server.

Based on `daeb1b0c` (dev, v0.1.508). Labels: READ, MEASURED, COMPUTED, INFERRED, OURS, OPEN.

## What retail does (READ)

From round 737's reading (`docs/protocol/opcodes/movement.md`, "0xB021 in full"), and this round's
reading of the stop (`movement.md`, "0xB023, the stop"), both decompiles on the box:

- **The request, 0x7021** (the client's `FUN_009ec570 -> 0x9ec240 -> 0x9ec080`): `01 | region u16 |
  x i16 | y i16 | z i16`, the raw region-local coordinates truncated, 9 bytes, once per accepted
  click. A dungeon destination is three i32. The sky click sends the heading form `00 | command u8 |
  angle u16` (`FUN_009ebec0`, command 1).
- **The handler** is `GObjPC::FUN_004b0ea0`. It refuses silently: dead, a running trade, the motion
  states 8 / 0x10 / CHANGEMOTION, the abnormal bits `0xc1 | 0x4000`, a kind other than 0 or 1, a
  destination outside the 3 x 3 regions (`FUN_0048c2d0`), and, while moving, a destination within
  5.0 (`0xb45b28`) of the one set.
- **The answer, 0xB021**, to every PC in the mover's 3 x 3 blocks, the mover included (`0x484d90 ->
  CMsgBlockObject::FUN_00534150`): `u32 uid | the movement | u8 flag | (flag 1) source region u16,
  x * 10 u16, y f32, z * 10 u16`. The client reads it in `NetProcessInNavAndSkill::FUN_008a5750`,
  registered for 0xb021 in its dispatch table (`funcs_010.c`, read this round).
- **No stream.** The server steps the mover itself (`CGObjMoverByDest::vslot_003`) and sends nothing
  per step and nothing on arrival.
- **The stop, 0xB023** (read this round): the CGObjChar slot-300 stop `GObjPC::FUN_004a9430(angle,
  send)` composes it when `send` is set -- `FUN_00430a00(0xb023)`, the uid (obj `+8`),
  `FUN_00487c80` (region, x, y, z f32 and the u16 angle) -- and sends it through the same 3 x 3 send
  (`FUN_00484d90`). It then sets a WALK or RUN character to STAND. The client registers 0xb023 ->
  `FUN_008a4f80`, which reads 4 + 2 + 0xe bytes and snaps the object there (`FUN_009e00f0`,
  `FUN_009e11e0`). So: `u32 uid | u16 region | f32 x, y, z | u16 angle`, 20 bytes.
- **The record of a player spawned moving** carries the mover's destination (`0x48be00`: has
  destination 1, the run flag, then the region and i16 x, y, z) or, with none, the mover's command
  byte and angle; the client aims a body that spawned moving (`FUN_009ca320`).

## What OpenSRO does now

### The wire

| Direction | Message | Form | Label |
|---|---|---|---|
| client -> server | **0x7021** | retail's: the destination form per click, the heading form per sky click | READ |
| server -> 3 x 3, mover included | **0xB021** | retail's: uid, the movement as asked, flag 1, the source where the server had the mover | READ |
| server -> 3 x 3 | **0xB023** | retail's: uid, region, x, y, z, angle -- a stop, a placement, a correction | READ form; when it is sent is OURS (below) |
| client -> server | OpMove 0x0022 with the **stop flag** (bit 2) | three f32 and the flags byte: where the walk stopped short of the point its 0x7021 named | OURS |
| client -> server | OpMove with the relocated flag | a placement, as before (round 637) | OURS |

`OpEntityMoved` is no longer sent. The client still reads it (an older server).

### The server (`server/internal/world/mover.go`, `server/internal/session/destmove.go`)

- **`proto.DecodeMovement` fixed first** (round 737's correction): a dungeon destination is three
  i32 and a field destination three signed i16.
- **0x7021** (`handleMovementRequest`): the READ gates OpenSRO has the state for -- dead, kind,
  CHANGEMOTION, the abnormal states that stop a move (`0xc1 | 0x4000`: stun, freeze, sleep, root) and
  an established trade (both added after the review, F4; the first version claimed "the gates OpenSRO
  has the state for" without them), the 3 x 3 regions, the 5.0 near-destination -- plus the round-640
  wall root, a height bound on the destination and a per-session rate bucket (OURS, both after the
  review, F10 and F8).
  A dungeon destination is dropped (OpenSRO serves none); a heading form without the forward bit
  (the arrow keys' turns, which OpenSRO's client binds no key to) is dropped. An accepted move stands
  a sitter (READ, `SetMotionState(WALK/RUN)`), cancels a running auto-attack, and goes out as
  0xB021 to the window that holds the mover and to the mover.
- **The leg** (`world.Mover`, OURS: the server has no navigation mesh for players, round 744): the
  hub keeps `{source, destination or heading, start, speed}` per mover. **Every copy the hub hands
  out carries the leg's position at that moment** (`outLocked`), so range checks, a monster's chase,
  a pick-up's reach, trade's 320, the party board, the spawn record and the saved position all read
  where the character is now. The leg is cut at its destination (READ: retail's mover never passes
  it). The speed is the run speed with buffs and a GM's `/speed` (`buffBooks.RunSpeed`); a change
  mid-walk re-bases the leg.
- **The mover pass** (`moverPass`, every 250 ms, OURS): it refiles the movers whose position crossed
  a block line -- the existing `afterRelocate -> crossPlayer` spawns and despawns -- and ends the legs
  that arrived. It runs only while somebody walks: the goroutine ends when no leg is left and the next
  accepted move starts it.
- **A stop report** (OpMove with the stop flag) or **a placement** (the relocated flag) is a claim,
  bounded as the review's "Review fixes", F1, below says (`world.Hub.Claim`). *As first shipped the
  bound had no clock and no anchor, and this file called it "the speed bound": it was not (the
  review's F1 moved a character 1,650 units in 8 ms).* A claim taken is relayed as 0xB023 to the
  window, not to the mover, whose client is there.
- **A claim the server does not take** puts the character back on the server's anchor and ends any
  leg, and the window -- the mover included -- hears that 0xB023 (`correctMover`).
- **Named points**: a placement may also land, once, within 2 minutes of being named, on a point the
  server itself named -- an arrival's point and the client's spawn spot there, a GM `/tp` or `/goto`
  point (`noteArrivalLanding`, `noteGMLanding`; F2). cmd/server's **`-trust-client-positions`** (QA
  only, default off) takes every claim, as before; `qa_shot.sh` passes it when the binary has it,
  since the QA hooks place the player anywhere.
- **The record** of a player on a leg carries the destination form (or the heading run's command and
  angle) and RUN (READ: the accepted move's `SetMotionState(2 + run flag)`), so a player who comes
  into view of a walker sees it walking.
- **A sit or a death** while the server's leg still runs ends it where the server has it and tells the
  window with 0xB023 (READ: the engine stops a walker, slot 0x4b0, before it sits). The client stops
  before it asks, and reports a stop short of its point first.
- **Regeneration**: a walker does not regenerate until its leg ends (STAND regen only, round 607's
  rule; `motions.walking`).

### The client

- **The local walk is unchanged**: it starts on the click and never waits for the server, so it feels
  exactly as before -- no rubber-banding. `MoveOrderSync` (`client/scripts/world/move_order_sync.gd`)
  decides, once a physics tick, what the walk owes:
  - a 0x7021 for a new order, or for one whose point, truncated as the wire carries it, moved more
    than 5.0 from the point sent (READ: the server refuses `<=` 5.0 on the truncated coordinates;
    exact since the review, F5). An approach re-aimed every tick at a moving target is sent only that
    often;
  - the heading form for a sky click's run, or a new heading;
  - the stop report when the order ended more than 3.0 short of the point sent (an approach in
    reach, the end of a heading run), **whenever a wall ended it**, and when the navigation graph has
    a wall between where the player stands and the point sent (review F6); otherwise a walk that ends
    within 3.0 says nothing, as retail's arrival says nothing (the stop distance 2.39 plus the wire's
    truncation);
  - **a refusal it was not told of** (review F3): READ, retail's handler refuses silently, so the
    client holds its last 0x7021 unconfirmed until its own 0xB021 names it, and with no echo within
    1.5 s (OURS) stops where it is and reports the stop;
  - a placement the walk cannot account for, as before.
  - `_flush_position` (before an attack, a pick-up, a sit) sends the stop when the player stands more
    than 0.5 from where the server will have it, so the request is measured from there.
- **Its own 0xB021** confirms the order it names and changes nothing else. **Its own 0xB023** is the
  server's correction: the player is put there, the order ends, and a stop is sent from there, so a
  0x7021 already in flight cannot start a leg this client does not walk (review F3).
- **Other players** (`OtherWalk`, `World3D._step_other_legs`): a 0xB021 starts a leg -- from where the
  body is drawn, or from the source when it has drifted more than `MonsterMotion.RESYNC_DISTANCE`
  (32, OURS: the monsters' rule) -- stepped every rendered frame at the player's run speed with
  retail's cut at the point (`MonsterMotion.step`, READ), the height resolved from the ground as it
  goes (the monsters' budget), turned at 3 pi rad/s. 0xB023 snaps the body and its facing. A spawn
  record with a destination or a heading run walks on. The run speed comes from the record's param
  24 and from every buff packet's runSpeed.
- **Keys and orders**: OpenSRO binds no movement key (`keymap.gd`: the arrows are NOT_BOUND), so the
  arrow keys' 0x7024 is not built (OPEN). Every order -- the ground click, the sky click, the attack
  and friendly-cast approach, the pick-up walk, the NPC talk approach -- goes through the same sync.
  There is no follow and no stop key in this client.
- `OPENSRO_QA_WALK_TO` (QA only) drives a client by ticks: ground clicks, a sky click, the sit toggle,
  an attack.

## Version skew

Client and server ship together.

- **An older client on this server**: it streams OpMove positions while walking and sends no 0x7021.
  The server takes each position as a claim -- 2.5 units a step at 20 a second, which the allowance
  pays for as fast as it accrues; a frame hitch's longer step is paid from what accrued during the
  hitch -- so it walks, and the window hears a 0xB023 per position: a round-749 client draws it in 20
  snaps a second. A step the bound refuses is corrected with a 0xB023 the older client cannot read,
  and its next steps are measured from the anchor, so it can be stuck until it walks back (as the
  review found for round 749's first bound; the allowance makes it rare). An older observer reads
  neither 0xB021 nor 0xB023, so it sees every player stand still, and its spawn reader refuses a
  walking player's record ("a destination in a player record") and drops that spawn. The client
  auto-updates, so this lasts one launch.
- **This client on an older server**: the server ignores 0x7021, so nobody sees this player move, and
  its stop reports read as walked positions. The release bumps both.

## Departures from retail (OURS), disclosed

- **The server does not step the mover**: it keeps the leg and computes the position (no navigation
  mesh for players, round 744). A wall is the client's to report (the stop flag on OpMove), and the
  window hears it one transit later than retail's server would send its own 0xB023.
- **The claim bound** (the anchor, the free 9, the banked second of run, the height of 100) and **the
  named points** (once, 2 minutes) are OURS. `/unstuck` (client-only) now lands only within an
  arrival's grace; after it, the server corrects it (OPEN: a server-side `/unstuck`).
- **0xB023 is not sent to the mover for a stop it reported** (its client is there), only for a
  correction. Retail's own stop goes to the mover too.
- **The observer walks a straight line** and does not run its own collision (retail's does), so a body
  can walk into a wall for a transit before the mover's stop snaps it back.
- **A source within 32 is not taken** (the monsters' resync rule): retail places the object at a flag-1
  message's source every time.
- **Flag 1 always**, as round 737 found safe.
- **The mover pass is 250 ms**; retail refiles the block as the mover steps.
- **A move does not end the move-ended buffs** (0xB072): OpenSRO's buff book has no such flag (OPEN).
- **The returning-home guard** (round 665) still applies to OpMove only: a 0x7021 sent before a warp
  home is in the old zone's regions and is refused by the 3 x 3 region rule when the zones are far
  apart; two adjacent zones are not guarded (OPEN, LOW).
