# Round 788, lane P: the account PIN ("Character Lock")

Branch `feat/acct788-p` from `feat/acct788` (`107c4a99`). The reference is `docs/protocol/pin.md`.

## What was asked

The account PIN, server and client. Round 788's research established that the retail game has no
PIN of any kind, so the feature is OURS, modelled on the user's screenshot of another private
server's addon: a "Character Lock" window over the select screen's harbour -- entry box, message box
("Enter your pin code. Only 4 digits allowed."), Remove Pin, a 3x4 keypad `1 2 3 / 4 5 6 / 7 8 9 /
C 0 <` (C and < on red tiles, digits on blue), "Remember this PC and don't ask for pin", a close X.
The user: "when entering the PIN on the verify stage (not creation) it picks a random position for
all of the digits to make it harder to steal the pin." The user's decisions (2026-10-15): per
account, asked once per login before the first Start / Delete / Restore; optional, an operator flag
can require it; 4 digits; 5 wrong entries lock it for 30 minutes across logins, persisted; Remember
this PC by a random device token whose hash the server keeps, forgotten when the PIN changes or goes.

Labels: **READ** (the binaries, through the research notes and charselect.md), **MEASURED** (the
archive on the render box, the runs below), **OURS**, **OPEN**.

## OURS (every choice)

Server:
- A new package `server/internal/charlock` (MemStore, SQLStore, `Service`), not
  `server/internal/account` (lane S adds punishments there).
- The tables `character_locks` and `character_lock_devices`, no foreign key to `accounts`.
- bcrypt for the PIN (said in pin.md: 10,000 values, the lockout is the protection); SHA-256 for
  device tokens; tokens of 16..128 printable bytes; at most 16 remembered PCs per account.
- The lock: the 5th wrong entry locks for 30 minutes and resets the count; a right entry resets it;
  a wrong Remove counts; the right PIN is refused while locked.
- A remembered PC passes even while the PIN is locked.
- Create, verify and remove each unlock the session; the unlock is keyed by account id on the
  session (a second login on one connection starts locked).
- No change operation: remove, then create.
- Opcodes 0x0120..0x0124 (0x0118..0x011F left to the round's other lanes); one reply opcode for all
  four requests, carrying the status; the lock as seconds left, not a time.
- The gate wraps the whole chain (`handle = session.CharacterLockGate(...)`, one line in main.go):
  Start 0x7001, OpEnterWorld 0x0020, 0x7007 actions 3 and 5; refusal 0x40e; fails closed on a store
  error; a session not logged in passes to the handlers behind.
- `-require-pin` / `OPENSRO_REQUIRE_PIN`, in `cmd/server/charlock.go`.

Client:
- The window's geometry: 318 x 294; left column (24, 48) 120 x 190 holding the entry (26 high),
  the message (104 high) and Remove Pin; the keypad panel (150, 48) 144 x 190 with 40 x 40 tiles
  6 apart; the remember row (24, 244) 270 x 26. Caption at (10, 11) as PartySettingsDialog's; close
  at (w - 26, 10) as the registry frame's chrome (UI_TODO rule 12). Tiles: the button art drawn
  square with its 5-pixel border kept (StyleBoxTexture margins), digits at font index 4.
- No OK button: the fourth digit submits (the screenshot has none). Create asks twice; a mismatch
  starts over.
- The verify shuffle: the ten digits in the ten digit cells, C at cell 9 and < at cell 11, a new
  order each time the window opens, from a generator seeded by `Crypto.generate_random_bytes`.
- **Keyboard digits do not type**, in any mode: the shuffle defeats a click recorder, the keyboard
  would hand the PIN to a key logger; one habit for every mode. Escape closes the window.
- The remember box shows in verify only; Remove Pin in verify / remove / locked.
- The words (OURS English; no textdata key exists), listed in pin.md.
- The device token: 32 random bytes as 64 hex, one per `host:port`, in `user://character_lock.cfg`
  (not `settings.cfg`, which holds nothing secret by its own rule). Never printed.
- `CharSelectLock`: the status asked when the select screen opens; Start and the delete/restore
  confirm held (`hold(retry)`, then the action runs again); a server silent for 3 s is taken to have
  no PIN; the Pin Code button one column left of Start, shown with the list's or the selected
  character's buttons; a 50 % black dim behind the window.
- QA hooks (QA only): `OPENSRO_QA_PIN=create:<pin>` / `verify:<pin>,<pin>...`,
  `OPENSRO_QA_PIN_REMEMBER=1`, `OPENSRO_QA_PIN_DELAY=<s>`; they press the window's own cells.

## OPEN

- **Merge with lane C** (its adapter for retail-protocol servers in CharacterSelect.gd): on a legacy
  session `_setup_lock` must not call `_lock.query()` (0x0120 means nothing to a retail server);
  everything else in the hook is inert without a status (`hold` passes when no status was asked).
- **Merge with lane N / S**: no file of theirs is touched except main.go (one line after the
  handler chain) and swarm's cleanup list; `session/lobbyhandler.go` is not edited -- the gate is a
  wrapper in `characterlock.go`.
- A retail client cannot enter a PIN (no window): on an account with one it lists but cannot start,
  delete or restore.
- No GM command to clear a PIN or a lock; the constants (5, 30 minutes, 16) are not flags.
- The select screen's message line can run under the Pin Code button on a narrow screen.
