# Round 788, lane S: the server side of logging in and of account bans

Round 788 is "Account & login to 100%". The user: "let's get the account and login section 100%.
Make sure you check the original code and make it as accurate possible and make no mistakes."
Lane S's part: the Go server's login decisions and account bans, matching the original's rules as
recovered, every front door through one service.

Labels: **READ** (seen in the binary on the RE box, with the address), **MEASURED**, **INFERRED**,
**OPEN**, **OURS**. Addresses are GatewayServer.exe's unless named. Base: `feat/acct788`
(`107c4a99`); branch `feat/acct788-s`.

## 1. What was asked

1. Flesh out `session.LoginService` (keeping `LoginAttempt`, `LoginOutcome`, `Login`): every front
   door -- the old OpLogin 0x0001 (still answered with a reason string), the new 0x6102, later the
   retail listener -- decides through it. Wrong passwords counted per name with the automatic
   block; punishments; inspection and full (today's `LoginGate`, moved in, GM accounts exempt);
   already connected; the per-IP limit; the store's failure.
2. Typed punishments in `account` (MemStore and SQLStore), the old `accounts.blocked` migrated.
3. GM commands: `/ban` as retail's (a kick), and OURS `/block`, `/unblock`, `/blockinfo`.
4. Flags with env twins; tests; docs.

## 2. What was READ

Most of it was already in RESEARCH sections 1 and 2 (`/root/opensro-acct788/RESEARCH.md`) and is
now in docs/protocol/opcodes/login.md, "The login reply, READ (round 788)" and "Punishments". New
this lane:

- **Which refusals close the connection.** The gateway's disconnect is the session manager's
  vtable+0x5c called with 1 (READ at 0x405e1d after a GlobalManager refusal and at 0x4071e3 after
  the last wrong password). The certify failure builder 0x40dc40 (`[2,2,1,..]` for a block, `[2,6]`
  for the rest) and its caller 0x40dc2a only call vtable+0x50 (the send) and +0x4c (INFERRED: the
  message's release): **a blocked account's connection stays open**. Neither is there a disconnect anywhere in 0x40d710-0x40de06,
  the shard check that sends `[2,5]` (full, 0x40d871). So: wrong password below the tolerance,
  blocked, full and the generic failure stay open; the last wrong password and every 0xA200
  refusal (already connected, the IP limit, inspection) close.
- **The certify job** 0x415e40 (content 22, `_CertifyTB_User`): result byte 0 -> in; 3 ->
  `_QueryBlockGuide` into a 0x210-byte buffer at certparam+0x42 (memset 0x415f4c), job 5; any other
  -> job 1 (wrong password); a query error -> job 3. The reason field is 0x200 bytes, so the
  server cuts a reason at 511 bytes (INFERRED: the terminator takes the last).
- **Type 2, "block login for inspection"**: the gateway knows only certify results 0, 3 and other
  (0x415f25-0x415f41); what `_CertifyTB_User` does with a type-2 row is inside the account
  database, which is not on the box (`find /` found only `/root/SRO_VT_SHARD.bak`). OPEN; OpenSRO
  treats it as a type-1 login block.
- **"Set Infinite Duration" is a date** (SR_UserPunishment.dll, the SMC plugin): the button is
  control 0x41a (its id at file offset 0x8c054 in the dialog resource), its click handler 0x10006610
  (message map entry at 0x1000401f). It calls `GetLocalTime` (import 0x1007507c) twice, adds 0x64
  to the second's `wYear` (`add WORD PTR [esp+0x10],0x64`, 0x10006635), and sets the first into
  controls 0x406/0x407 and the second into 0x408/0x409 through helper 0x10017ef0
  (`SendMessage(.., 0x1002 DTM_SETSYSTEMTIME, GDT_VALID, ..)` on each). The dialog labels those
  pickers "Punish Begin Time" (y 0x8e) and "Punish End Time" (label y 0x9d, pickers y 0x9c). So an
  infinite punishment is stored as begin + 100 years, local time. OpenSRO keeps end NULL in its
  table and puts begin + 100 years on the wire.
- **The automatic punishment's executor** is the `AutomatedPunisher` config key's value (READ
  string 0x12a850 in GlobalManager.exe; MEASURED value "AutomatedPunisher" in the package's
  server.cfg). The package's guide and description texts were not copied; OpenSRO's default guide
  is its own.
- **GlobalManager's admission order** (0x401b70): the logged-in check (0x402220, error 1) first,
  then the per-IP checks (errors 2 and 5); inspection (3) after (0x401d36).
- **Correction:** docs/protocol/opcodes/login.md had `0x6111`/`0x6112` the wrong way round and
  named AgentServer as their receiver; `0x6111` is the failure, `0x6112` the success, both to
  GlobalManager (RESEARCH, READ 0x406b45 / 0x406ccf). Corrected in both places it said so.

## 3. What was built

**`session.LoginService`** (`server/internal/session/loginservice.go`, `onlineaccounts.go`). The
exported API is unchanged; added: `LoginService` fields `Status`, `Staff`, `Online`, `Rules`, `Now`,
`Location`, `Logger`; `LoginRules`; `OnlineAccounts` (`NewOnlineAccounts`, `Claim`, `Release`,
`Session`, `Count`); `SessionEnded`; `LegacyReason`; `LoginHandlerFor`. `LoginGate` is gone (its
words stay, `LoginRefusedInspection` / `LoginRefusedFull`). `LoginHandler(store)` keeps its
signature (a service of its own, for tests and tools). The decision, in retail's order:

| Step | Reply | Close | |
|---|---|---|---|
| a second login on a logged-in connection | `[2,3]` | no | OURS |
| wrong ID/password below the tolerance | `[2,1,max,used]` | no | READ |
| ... reaching it | `[2,1,max,used]` + count cleared + type-1 block | yes | READ |
| active login punishment (types 1, 2) | `[2,2,1, guide, end]` | no | READ (type 2 OURS) |
| store error | `[2,6]` | no | READ |
| full, not a GM account | `[2,5]` | no | READ (exemption OURS) |
| already logged in elsewhere | `[2,3]` | yes | READ, old session untouched |
| per-IP limit reached | `[2,8]` | yes | READ (off by default OURS) |
| inspection, not a GM account | `[2,2,2]` | yes | READ (exemption OURS) |

**Punishments** (`server/internal/account/punishment.go`, both stores): `Punishment` (serial,
account, type 1-4, executor, guide, description, raised/begin/end, end zero = infinite),
`PunishmentStore` (`AddPunishment`, `Punishments`, `ActivePunishments`, `EndPunishments`),
`AccountLookup` (`AccountByName`, `AccountByID`), `BlockedError` (matches `ErrBlocked`; carries the
punishment). `Authenticate` checks the password, then the active login blocks. SQL: table
`account_punishments`; the migration moves `accounts.blocked = TRUE` rows into infinite type-1
punishments with their `block_reason` and clears the flag in one statement (a CTE), so it runs once.
`Account.Blocked` / `BlockReason` are gone; `SetBlocked` stays, writing and ending punishments.
`character.OwnerStore.ByName` (new, `owner.go`) finds a character on any account without case.

**GM commands** (`server/internal/gm/accounts.go`, `session/gmsessions.go`): `/ban`, `/block`,
`/unblock`, `/blockinfo`, documented in docs/DEBUG_TOOLS.md.

**Flags** (cmd/server, deploy/README.md "Logging in"): `-login-failure-tolerance` (3),
`-login-failure-block-min` (10), `-login-punishment-guide`, `-max-users-per-ip` (0), each with an
`OPENSRO_*` twin. Bad values stop the server. The login hook is the last disconnect step.

## 4. OURS, each choice

- A second login on an already logged-in connection: `[2,3]`, the connection kept, nothing changed.
- A successful login clears the name's wrong-password count (retail: the image code's success).
- A name's count is forgotten an hour after its last failure (`LoginFailureExpiry`; retail OPEN);
  the table is swept at most once a minute.
- Counts are per name **as typed** (the store's usernames compare exactly); a name with no account
  is counted the same and gets no block (retail's procedure takes the name; what it does with an
  unknown one is OPEN).
- The password is checked before the block (whether `_CertifyTB_User` does is OPEN).
- The default guide "Too many wrong passwords. Please try again later." (retail's is the operator's
  config text); the automatic block's description "automatic: N wrong passwords".
- The per-IP limit is off by default (retail's `MaxUserForNonePCBangIP` has a value in its config;
  a LAN party or the bot swarm would trip it).
- GM accounts pass inspection and a full server (round 679's rule kept).
- Several active blocks: the one ending last is shown (an infinite one first).
- An account is released for a new login only by the gateway's OnDisconnect, after the world hook
  has saved the character (the hook order in cmd/server).
- `/ban`: the in-world name matched exactly, then without case.
- `/block`: durations `Nm`/`Nh`/`Nd` up to 3650 days or `forever`; the reason as typed after the
  duration, cut at 511 bytes, default "Blocked by a game master."; executor the GM's account,
  description "GM console: /block by <account> as <character>"; refused for a GM account
  (safety: a GM cannot lock another GM, or the operator, out from inside the game; the operator
  removes the name from `-gm-accounts` first) and for an account already blocked (the SMC's "user
  already blocked"); the account is disconnected wherever it is (the logged-in table reaches
  character select, the world hub the rest). `/unblock` ends both login types, future blocks
  included. `/blockinfo` shows the newest 5.
- The old `accounts.blocked` / `block_reason` columns are kept, unread, so an older binary rolled
  back still starts (it then sees no account blocked).
