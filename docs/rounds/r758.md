# Round 758: European axes and Egyptian set daggers -- the model was there, the log was wrong

The user's live log (v0.1.511) printed, among others:

```
USER ERROR: SkinnedBsrAssembler: item item\europe\weapon\axe_11.bsr not found in archive   (also axe_01, axe_03, axe_06)
USER ERROR: SkinnedBsrAssembler: item item\etc\weapon\eu_axe_11_set_b.bsr not found in archive
USER ERROR: SkinnedBsrAssembler: item item\etc\weapon\eu_dagger_11_set_a.bsr / eu_dagger_11_set_b.bsr not found in archive
```

The brief's hypothesis was that European axes, like daggers, are left/right pairs and that
`CharacterAppearance.item_models` paired only daggers, so these weapons drew nothing. **The
hypothesis is false.** `item_models` already pairs TypeID4 9 (dual axe) and 13 (dagger), which is
retail's rule, and every one of these weapons draws both halves. The errors came from the
character-template look-ahead (`template_paths`, round 748). It always listed each `_r` / `_f`
model's plain fallback, and the archive has no plain `.bsr` for any dual axe or set dagger. So
every one logged a "not found" for a weapon that drew in full. The look-ahead now asks for the
fallback only when the `_r` / `_f` fails, as the client and `build()` do.

Based on `155822c1` (dev). Labels: READ (decompile), MEASURED (run here), OURS.

## The retail rule (READ, `/var/tmp/decomp_client`)

Three sites build the dual-wield names, and all three test the same thing:

- `CObjCharacter::FUN_00a5f4f0`, which puts a worn item on a body. It requires the type word to
  be TypeID1 3 (`& 0x1c == 0xc`), TypeID2 1 (`& 0x60 == 0x20`) and TypeID3 6
  (`& 0x780 == 0x300`). Then:
  - `uVar1 >> 0xb == 9 || == 0xd`: the path minus `.bsr` plus `"_l.bsr"`, loaded (asserting
    `pLoadObjHand`), then `"_r.bsr"`.
  - `== 0xe` with the body a woman (vtable `+0x34`): `"_f.bsr"`.
  - Otherwise, or when the `_f` or `_r` slot is empty, `LAB_00a5f851` loads the plain path.
- `icscriptobj::FUN_009e3890` (the script object's model): `*puVar7 >> 0xb` is 9 or 0xd gives
  `_l` then `_r`; 0xe with `param_2 == 0` gives `_f`.
- `FUN_0080b980`: the same TypeID test with `>> 0xb == 9 || == 0xd` gives `_r.bsr`.

So the pairing keys on TypeID 3/1/6 with TypeID4 9 (dual axe) or 13 (dagger) only. The folder
plays no part, so `item\etc\weapon\eu_*` pairs as `item\europe\weapon\*` does. A harp (14) is `_f`
on a woman. Every other weapon kind and every shield uses its own path. `item_models` was already
exactly this.

## The census (MEASURED, `client/tools/census_weapon_models.gd`)

The census tool is new. For each item row (`ItemTableReader.load_all`) with a weapon or shield
visual slot and a model, on a Europe man and a Europe woman, it counts two things:

- **draw**: `item_models` with each missing `_r` / `_f` replaced by its plain fallback (`build()`'s
  rule). A miss is a model with neither file in Data.pk2. Misses are split by whether any of the
  item's own files (plain, `_l`, `_r`, `_f`) exists.
- **ask**: the item's paths in `template_paths` that are not in the archive. Each one is a "not
  found in archive" error in the log.

The rows are 6640 item-sex pairs over every weapon kind (3/1/6/2..16) and shield (3/1/4/1..2).

| | draw misses, files exist | draw misses, no file at all | look-ahead asks for a missing file |
|---|---|---|---|
| before (dev `155822c1`) | **0** | 48 | **522** (50 paths) |
| after | **0** | 48 | **64** (17 paths) |

Per kind before → after, for the asks: 6/9 dual axe **414 → 0**, 6/13 dagger 50 → 8, 6/14 harp
18 → 16. Everything else is unchanged.

- **The 48 draws with no file** are the 24 `*_11_SET_{A,B}_RARE_SWITCH23` rows of every kind
  (each on a man and a woman). They name `*_23.bsr` (`blade_23`, `sword_23`, `shield_23`,
  `dagger_23`, `harp_23`, ...). The archive has none of these in any variant, so no rule could
  draw them.
- **The 64 asks left** are those same `_23` files, plus a woman's `_f` for `harp_14`, `harp_16`
  and `harp_22`. Those three have a plain model but no `_f`, and retail asks for the `_f` first
  too. The plain one then draws (fallback).

## The change

- `CharacterAppearance.template_paths` no longer lists `_fallback_of(m)` for every `_r` / `_f`
  model. The fallback is still made when it is needed:
  - `_prep_task` makes it when the `_r` / `_f` fails.
  - `_prepare` adds it for a cached failed template whose fallback has none.
  - `build()` falls back on the main thread as before.
- `item_models` is unchanged; it was already retail's rule. Its doc comment now cites the three
  READ sites and the census.
