## 1. `TIME_PROCESS` is not script time (READ)

The task named "about 56 ms of `TIME_PROCESS`" as the per-frame script cost. Godot 4.2.2's own
source says otherwise (`main/main.cpp`, `Main::iteration`, l. 3679-3736):

- `process_ticks` runs from before `SceneTree::process` to after `RenderingServer::draw`: every
  `_process` callback, the message queue's flush and **the whole render on the CPU**;
- `Performance.TIME_PROCESS` is set once a second to `process_max`, **the longest** such frame of
  that second (reset at l. 3734), not the mean;
- `TIME_PHYSICS_PROCESS` is likewise the longest single physics step of the second.

So the probe's `process_ms` (the mean of that monitor) was the worst process-plus-render of each
second. It is kept in the step line for comparison with older rounds, and no longer used here.

**What measures it instead: `FrameSplit`** (`client/scripts/world/frame_split.gd`, QA only, made by
the probe). Two marker nodes sit at the ends of the tree's process and physics order (SceneTree
sorts a group by `process_priority`, then tree order) and RenderingServer's `frame_pre_draw` /
`frame_post_draw` signals mark the draw, so a frame splits into:

| Phase | From -> to |
|---|---|
| `phys_cb` | first to last `_physics_process` of each step, summed over the frame's steps |
| `phys_engine` | the rest of each step: NavigationServer3D.process, the message queue (the deferred `Skeleton3D` updates of a pose made in a physics callback), PhysicsServer3D.step, the next step's sync |
| `proc_cb` | first to last `_process` callback |
| `post_flush` | the message queue flush after the process callbacks, the transform notifications (`SceneTree::process` l. 512 flushes them after `_process`), RenderingServer::sync |
| `draw` | RenderingServer::draw: the scene update (`rs_setup`, `get_frame_setup_time_cpu`: dirty instances, skinned AABBs), each viewport's render (`rs_main_cpu`, `rs_overlay_cpu`), the canvas |
| `post_tail` | audio, ScriptServer::frame, input, the frame timer |

Inside them the code adds its own timers while the probe runs (`w_*` World3D's `_process`, `p_*`
its physics step, `fx_*` EquipFx, `dress` each body's dressing). The probe prints one
`QA CROWD split` line after every step line and one for the arrival.

## 3. Built

### 3.1 Arrivals: character templates on a worker thread (item 3)

**Where an arrival frame went (MEASURED, `QA DRESS`, every dressing over 40 ms by phase):** the
first body of a new kind spent 220-378 ms of its 263-400 ms in `CharacterAppearance.build`
assembling its body and item templates (`body_assemblies+1 item_assemblies+1..4`); a cached kind
dresses in 5-10 ms.

- **`CharacterAppearance.prepare(ref, items)`** (OURS) works out what a build would assemble
  (`template_paths`: the worn models with build's own slot rule, each `_r` / `_f` model's plain
  fallback (READ 0xa5f4f0), the default wear (READ 0xa5e010), the glow's particle files at the
  item's plus) and starts a WorkerThreadPool task for the missing body and item templates, as the
  monsters' species templates have been made since round 661. `poll_prepared()` adopts finished
  tasks on the main thread; `build()` is unchanged and, with everything cached, only duplicates.
  - The task assembles a new body (`SkinnedBsrAssembler.assemble_from_archive`) and parses its
    stand and run clips in the held weapon's group into the new template's own clip cache (the
    first body's clip lookup had read them on the main thread). Items are assembled onto the new
    template's skeleton, or onto a copy of an existing template's skeleton made on the main thread.
  - **No `Node.duplicate()` on the worker** (READ, Godot 4.2.2 `scene/main/node.h`:
    `ERR_READ_THREAD_GUARD` -> `is_readable_from_caller_thread` ->
    `is_current_thread_safe_for_nodes`, false on a pool thread whether or not the node is in a
    tree). The first version duplicated there: 14,460 `can only be accessed from either the main
    thread` errors in one 1000-body boot, and every copy's Node3D properties came back as
    defaults. Items are now attached in place and lifted off (`_item_template_on(..., in_place)`):
    a shared-skin skeleton already has the object-space bone, the only bone attaching adds. 0
    errors since.
  - **The task's copy of an existing template's skeleton is its bones only**
    (`_bare_skeleton`). The round's first version handed it a `duplicate()` made on the main
    thread and freed it on the worker: its mesh nodes shared the template's meshes, and freeing
    them disconnected them from the shared meshes' `changed` signal off the main thread while the
    main thread connected new bodies to it. Godot 4.2.2's Object signal map has no lock (READ:
    `core/object/object.h` has no signal mutex; `MeshInstance3D::set_mesh` connects
    unconditionally, `scene/3d/mesh_instance_3d.cpp:113-122`). MEASURED: one 200-body boot
    (`F200`) crashed during its arrival, `FATAL: Index p_index = 0 is out of bounds (size() =
    -995350686)` on the main thread. After the fix: 4 more boots at 200 and 1000, no crash.
    **Corrected after the review (F1):** that crash was not this race. Its cause was a `const`
    Array read by the task and the main thread together (section 9); the bones-only copy stays
    (it removes a real race), but it did not stop the crash, which the review's stress reproduced
    18 times in 19 runs on this code.
    EfpEffect's caches are now written and evicted under the lock its preload task reads under
    (`_texture`, `_mesh`, `_evict_kind` read or wrote them unlocked).
  - **One skin a body still holds** (round 738's A2): a new template goes onto its layout's shared
    skin at adoption (`share_template`), and the task's item templates are moved to it too
    (`_reskin`).
  - **At most 2 tasks run** (`PREP_MAX_RUNNING`, OURS), low priority, the rest queued in request
    order (nearest body first). 52 at once took the main thread's share of the CPU and the archive's
    lock: arrival frames of 1.5-2.2 s (MEASURED, `h1000c`).
  - The glow's particle files go to EfpEffect's own preload task; a kind is ready only once each is
    decoded with its textures and meshes (`EfpEffect.is_preloading` now holds until the textures
    are in, not just the template: the first weapon effect of the arrival was otherwise made while
    its first texture was still decoding, and decoded it again on the main thread, 140 ms
    MEASURED in `h20`'s `QA EQUIPFX master` line).
- **The world** (`_other_template_ready`): the build queue's pump asks before dressing a body; a body
  whose kind is not ready stays queued and the next nearest is tried. The answer is kept per kind
  (body, worn items, pluses) and asked again only after the appearance adopts something
  (`prep_generation`). `OPENSRO_QA_SYNC_TEMPLATES=1` dresses the old way.
- **The archive's lock** (`Pk2Reader._read_block_chain_locked`): held for the cache lookup, each
  block's seek and read and the cache insert, no longer through the Blowfish decrypt and the
  entry parse of a whole directory chain. A worker's first look into a large directory stalled
  every main-thread read behind it.
- **The pump** (`OtherCrowd.BuildQueue.pump`): one native sort a frame of (distance, arrival)
  packed into an int, instead of a scan of the queue for each body dressed; a second pump in the
  frame of a full pass looks only at the bodies queued since (the lineup's 1000 unbracketed spawns
  each pumped the whole queue: O(n^2), about 0.5 s of the spawn frame once nothing was ready),
  and the queue is looked at whole again once templates are adopted (`reopen`).
- **The budget follows the frame** (`BuildQueue.note_frame`, OURS): each frame may dress for
  `HITCH_TARGET_USEC` (90 ms) less the last frame without its dressing, at most the old 25 ms, at
  least one body. With the 1000-body frame at 85 ms the queue dresses about one body a frame
  instead of adding 25 ms to it.
- **Fades once a frame**: `AppearFade.step` ran in every physics step (each of an arrival's dozens
  of fades setting its twins' alpha); it now takes the frame's steps' time once in `_process`. The
  alpha a frame draws is the one its last step reached. OURS detail: a fade started inside a
  physics step is stepped with that whole frame's time, at most one frame ahead at its start.

### 3.2 EquipFx (item 2)

- **One master per effect file, not per (file, scale)** (`EquipFx.kind_key`). A master is simulated
  at the world origin with no scale; the holder carries the row's scale (`holder_transform`), and
  every master of a file has the same template and seed. The 1000-body lineup's weapons and
  shields named **13 kinds over 6 files** (`QA CROWD census: equipment effect kinds`, MEASURED:
  `enchant_a_01` at 5 scales, `enchant_b_01` at 2, `enchantbow_a_01` at 3). Now 6 masters.
  Hosts stay per (bone, file, scale). **Corrected after the review (F7), OURS:** each master had
  its own random stream (`EfpSim._init` randomizes; the seed is not fixed), so weapons of one file
  at different row scales showed different particles before; now every weapon showing a file shows
  the same particles at the same moment, each at its own scale and turned with its own bone. In a
  crowd that is identical sparks on every enchanted weapon of a file (one master per (file, scale)
  already did that for the weapons of one scale, since round 734). A per-holder phase into the
  shared stream would need a buffer of past frames per master and a MultiMesh swap per holder per
  step; not built.
- `fx_effects` at 1000: 6.4-6.8 -> 3.5 ms a frame (efp steps 27 -> 14 a frame); the frame with
  EquipFx off is now 5 ms under the frame with it (85 -> 80), against 15 before (h1000a).
- The per-weapon own simulation (`OWN_BUDGET` = 1, the user's decision) is unchanged: it is 2 of
  the 8 effects stepping at 1000.
- Not changed: the driver (0.8 ms: the spread scan of 1,386 hosts, the 64 holders placed), the
  64-holder budget.

## 9. The review's fixes (`docs/rounds/r748_review.md`) and the merge with round 747

### F1: the crash, and the const audit

**F1 (CRASH).** `_fallback_of` looped over `const _FALLBACK_SUFFIXES` on the template task while
the main thread did the same. A GDScript `const` Array is read-only, and Godot 4.2.2 reads a
read-only Array's element through one Variant slot that every reader shares (READ, the review:
`core/variant/array.cpp:84-98`). Two threads swap Strings through that slot with no lock, and the
heap breaks. `_fallback_of` now reads no constant (`ends_with("_r.bsr") or ends_with("_f.bsr")`).

**Which reads are a risk (READ, Godot 4.2.2):**
- **Read-only:** only `const` initialisers are folded into read-only values
  (`modules/gdscript/gdscript_analyzer.cpp`: `make_array_reduced_value` and
  `make_dictionary_reduced_value` call `make_read_only`, nested literals included; a `var` or
  `static var` literal is not folded, `:1899`). So a `static var` Array hands out its element
  itself.
- **Arrays:** the VM's `for` (`array->get(i)`), `CONST[i]` and every element method go through
  the shared slot. `in` / `has` / `find` / `size` read the storage directly (`Array::find`) and
  are safe.
- **Dictionaries:** the keyed read (`VariantKeyedSetGetDictionary::get`, const `getptr`), the
  named read (`get_named`, const) and the `for` over keys (`next`) do not touch the slot
  (`dictionary.cpp:114-120`, `variant_setget.cpp:985-993`, `gdscript_vm.cpp` ITERATE
  DICTIONARY). But a Dictionary's nested Array values are read-only Arrays.
- **Packed arrays** have no read-only slot.
