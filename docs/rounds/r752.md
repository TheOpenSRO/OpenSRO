# Round 752: party matching shows only one page

The user, testing on the live server with thousands of swarm bots listed in party matching: "fix
pagination in the party matching. It only ever lets you see 1 page".

Based on `b3962b8d` (dev, v0.1.510). Labels: READ (from the binaries), MEASURED (run here), OURS
(a decision of this project), OPEN.

## The cause

**The page spin's arrows never worked.** `UiBuilder._build_spin` connected each arrow like this:

```
btn.pressed.connect(func() -> void: _spin_step(ctrl, step))
```

`_spin_step` is a `static func` of `UiBuilder`, and `_build_spin` is an instance method. Godot
4.2.2 builds a lambda that names nothing of its instance except a static as a lambda with no self,
then calls the bare name on that null self. So every click on either arrow failed with:

```
SCRIPT ERROR: Invalid call. Nonexistent function '_spin_step' in base 'Nil'.
```

The value never moved, no 0x706c went out, and the window stayed on page 0. That is the user's
"only ever lets you see 1 page". The warehouse's page spin, `GDR_STORAGE_SPIN_PAGE`, is built by
the same function and was broken the same way.

The evidence:

- **MEASURED, live, before the fix.** A headless client on the box ran against a local server
  holding 300 swarm entries (14 pages). The QA step clicked the spin's Right arrow with real mouse
  events, `Input.parse_input_event` at the arrow's centre.
  - The arrow was the topmost control under the point (`QA MATCH UNDER`: the window, its frame,
    the spin, then `Right`, a TextureButton with filter STOP).
  - It received the press and the release, and emitted `pressed`.
  - The lambda then raised the SCRIPT ERROR above.
  - The state stayed at "page 0 of 14", the label at "1".
  - Asking for page 13 directly, bypassing the spin, worked at once: "13 of 14, 1 row, entry 300".
    So the server and the client's parsing were both sound.
- **MEASURED, a probe in a bare Godot 4.2.2 project on the box.** The same static, reached from a
  lambda four ways:

  | how the lambda calls the static | result |
  |---|---|
  | bare name, lambda made in an instance method | NOT reached (the same SCRIPT ERROR) |
  | qualified `Holder.bump()` | reached |
  | bare name, but the lambda also touches a member | reached |
  | bare name, lambda made in a static func | reached |

- **MEASURED, the rest of the client checked.** A scan of every one-line lambda in
  `client/scripts` for a bare call to its own class's static found 8. Seven are made inside static
  functions (`video_options`, `efp_effect`, `audio_bank`, `npc_talk_view`, two in `ui_builder`),
  and the probe shows that form works. The eighth is this one. Multi-line lambdas were not
  scanned.

## Not the cause (checked)

- **The server's page reply.** READ, `sm:0x450d20` and the page builder `sm:0x451630`:
  - the reply is `[1][page count][page index][n]`;
  - pages close at 23 (`cmp al,0x17`);
  - an index at or past the count is answered as page 0 (`uVar4 <= local_1a` → 0);
  - more than 0xfe pages asserts.

  `party.Matcher.Page` does exactly that. MEASURED with a scratch Go client, `pageprobe`, against
  the local server with 300 entries:

  | asked | pages | index | rows | entries |
  |---|---|---|---|---|
  | 0 | 14 | 0 | 23 | 1..23 |
  | 1 | 14 | 1 | 23 | 24..46 |
  | 2 | 14 | 2 | 23 | 47..69 |
  | 12 | 14 | 12 | 23 | 277..299 |
  | 13 | 14 | 13 | 1 | 300 |
  | 14 | 14 | 0 | 23 | 1..23 |
  | 200 | 14 | 0 | 23 | 1..23 |

- **The request.** READ `c:SendPartyMsg_06c 0x81d090`: one u8, written by `0x508fe0(&page, 1)`.
  The client sends the same.
- **The client's parse.** READ `c:0x8841f0`: the first u8 goes to `local_b8`, the second to
  `local_b4`, and `0x97b930(local_b4, local_b8)` stores them at `+4` and `+5` of `0xeeec58`. The
  asm is `mov ecx,0xeeec58` at `0x884280`, then `mov [ecx+4],al` and `mov [ecx+5],dl` in
  `0x97b930`. So `+5` is the count and `+4` the index. `0x73b5b0` sets the spin's top from
  `DAT_00eeec5d - 1`, the count less one, and looks the page up by `DAT_00eeec5c`, the index.
  `PartyMatchNet.decode_page` reads count then index, which matches.

## How the original's spin behaves (READ)

The page spin is a `CIFSpinButtonCtrl`. Its own functions:

- **Fields.** The constructor `0x657f30` sets min (`+0x37c`) to 0, max (`+0x378`) to 1 and value
  (`+0x380`) to 0.
- **The arrows.** Left (`0x658120`) runs when min < value: value - 1. Right (`0x658160`) runs when
  value < max: value + 1. Each then redraws the label and notifies its window.
- **The label.** `0x657fb0`: `swprintf("%d", value + 1)`. A 0-based page 0 reads "1".
- **The setters.** `0x658010` stores the max and nothing else: no clamp, no redraw. `0x658050`
  stores the value; `0x658060` reads it.

What the Party Matching window does with it:

- **On a page.** `0x73b5b0` runs `0x658010(count ? count - 1 : 0)` and nothing more. No caller
  of `0x658050` is in `CIFPartyMatch`: its callers are `0x6cff20`, `0x6d30f0`, `0x74c100`,
  `0x74d2e0` and `0x807e30`, all other windows. So **the window never sets the spin's number from
  a page**. If the server clamps a page to 0 (the list shrank), the number stays where the player
  left it.
- **On a step.** The spin's handler is `0x732630`. When the HUD request queue is empty
  (`0x6ec4b0(6) == 0`), it deselects the slot (`0x740ca0(0)`, `+0x7ec = 0`). Then it runs
  `0x732610(value)`: `0x97c960(0)` on `0xeeec58`, then `SendPartyMsg_06c(value)`.
- **Refresh** (`0x732a80`) sends the same `0x732610(0x658060())`.
- **Opening.** `0x79c170(1)` creates the "PartyMatch" window only when none exists
  (`0x799680() == 0` → `0x79ac50`). Its close, `0x79c170(0)`, hands the name to `0x8b59f0`. That
  `0x8b59f0` removes the window is INFERRED: it is the only reading under which the open path
  can run again. So every open starts with value 0 and the label "1", and
  `CIFPartyMatch::Create` sends page 0.

## The fix

- **`ui/ui_builder.gd`**: the arrows call `UiBuilder._spin_step(ctrl, step)`, qualified. This one
  line is the fix. It also repairs the warehouse's page spin.
- **`ui/hud/party_match_window.gd`**, the window brought in line with the original's spin:
  - a page sets only the spin's top, `max(0, count - 1)`. Before this round, `refresh()` also
    forced the number to the reply's index, which the original never does;
  - the spin's handler `on_spin` deselects the slot, then asks for the page (`0x732630`);
  - `on_shown` puts the spin back to 0 and "1". The original builds a new window on each open;
    this one is kept, so it is reset (OURS, to the READ end state).
- **`ui/hud/party_match_qa.gd`**, the QA steps:
  - `spin:right|left` clicks the arrow with real mouse events and lists the controls under the
    point;
  - `click:<control>` gives any control of the window the same click;
  - `pagestate` prints the page and the spin;
  - `page:<n>` now goes through the spin.

The server is unchanged: it was already retail's.

## OPEN

- **A page request also clears the registration record** (READ). `0x732610` runs `0x97c960(0)`
  with `ECX = 0xeeec58`; `0x97c960` adds 8, so `0x97c3b0` clears the record at `0xeeec60`. The
  reply's row 0 then fills it again (`0x97c960(row)` → `0x740c30`) when the row is the player's
  own.
  - `PartyMatchState.request_page` does not clear it. The server puts the owner's entry first on
    every page, so this differs only when a reply is a refusal or the entry has gone.
  - Not done this round, because our window recomputes its enable rules from the live state on
    every pass (`_apply_buttons`). Clearing the record at the request would make Join, Change and
    Delete flicker until the reply, which the original, re-running its rules only on events,
    does not show.
- **The HUD request-queue guard** (`0x6ec4b0(6) == 0`) on the spin, Refresh and Join is not
  modelled. This client keeps no such queue.
