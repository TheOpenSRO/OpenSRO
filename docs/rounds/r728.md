## The stack count (READ; `client/scripts/ui/item_count_label.gd`)

- **Images, not a font.** `CIFSlotWithHelp::vslot_010` (0x66b460) loads
  `interface\item_number\item_number_%d.ddj`, ten 8x8 RGBA images. The glyph sits at the image's
  top-left and the image has a dark rim on its right and bottom. That rim is the "black border"
  the user saw.
- **Position.** `FUN_0067bd70` writes the count with `_itoa_s` and draws it from the last digit:
  - the first quad's left edge is `x0 - 2 + 4n`, and each next one is 5 px further left;
  - every digit is drawn at `y0 + 2`;
  - each quad spans (x - 0.5)..(x + 7.5), i.e. exactly 8x8 pixels.

  So the digits overlap by 3 px, and a 4-digit count starts 1 px left of the slot.
- **When.** `vslot_013` (0x685e50) draws the count only when `FUN_00680da0` holds: the item is an
  expendable (not bionic, TypeID1 3, TypeID2 3) and its stack is non-zero. A count of 1 is drawn
  too.
- **Square item slots are no longer clipped** (`UiBuilder._build_slot`). The clip cut off the
  first column of a 4-digit count. Row slots stay clipped.
- **Measured against `qty_Pp886X3.png`** (live run 2, frame `09_deposit_box`, bag slot 1 = 5000).
  - In both images the white glyph pixels of "5000" start **2 px left of the icon's light frame**
    and **1 px below its top row**.
  - The reference's rows 294-300 and ours, rows 234-240, are the same character strings, pixel
    for pixel.
  - In the reference, a 1-digit "9" starts at frame + 1, which is the 3 px the formula predicts
    between 1 and 4 digits.
  - The first run, with the clip still on, lost the '5's first column. That is how the clip was
    found.

## Splitting a stack (READ unless marked)

- **The trigger.** Shift+click on a bag stack (`CIFSlotWithHelp` click 0x681903 calls fill
  0x6b3fa0). It only opens for a stackable item (`0x538410`) with a count of 2 or more.
- **The box.** `CIFMessageBox` mode 5, `MsgBoxDivideCount` (`0x640020`), built as the
  inventory's one box (+0x390).
  - Size 300x183 (`push 0xb7; push 0x12c`), titled `UIIT_STT_INPUT_BOX` ("Input window").
  - Members: 11 icon, 12 name board, 15 retained count, 17 edit, 220 OK, 221 Cancel.
- **The fill.**
  - Retained count = the whole stack.
  - The edit's style is 3, its text "1" (`0xd87bdc`); it takes focus.
  - No minimum; the maximum is the stack - 1 (`0x634f20`).
  - The name goes on the board.
- **OK** (`0x63d920`) reads the edit as a 64-bit number and posts 0x8076, flagged 0 when the edit
  is empty or 0. In that case nothing is sent; that the owner checks the flag is INFERRED.
- **What OK sends (OURS).** The typed count moves into the bag's first empty slot; with no empty
  slot, nothing is sent. Retail sends 0x7034, which OpenSRO does not speak, so our own move
  message gains an optional trailing count (`InventoryMoveRequest.Count`; an older 3-field request
  still decodes as a whole-stack move).
- **The server.** `inventory.Splitter` (mem and SQL; the SQL one is a single transaction) needs an
  empty destination and 0 < count < stack. The new stack keeps the source's variance and
  durability.
- The layout matches `split_z4uFWIL.png`, down to "Retained numbe5000Distributed numb" running
  together as the original's statics do (frame `03_split_typed`).

## Buy back

- **The row** is `GDR_STORE_ICON_SLOT_01..05` under "Buy back" (READ, round 724). It is filled
  from the server's list, newest at the left (INFERRED), and its counts are drawn by
  ItemCountLabel.
  - The original's slot-type gate for that row is not read (INFERRED: the same CIFSlotWithHelp
    draw).
  - The list is requested when the store opens and after every sell or buy back.
- **The box (READ, new).** A buy-back slot is source kind 0x45. Putting it on the bag goes
  `CIFInventory::vslot_028` 0x6b5b80 → fill `0x6b0520`, which:
  - builds the inventory's box (+0x390) in mode 6, purpose 0x14;
  - prices it as "%I64d" of the item reference's +0xb8 (the **sell price**) times the count;
  - fills the count with the slot's own.

  Our box fixes the count at the entry's. That it cannot be lowered is OURS; the edit is restyled
  digits-only with no Backspace.
- **The server (OURS).** `shop.Service` keeps a book in memory: 5 entries a character (the 5
  slots), newest first, written by every successful `Sell` (Ctrl+sell included).
  - The book survives relog but not a server restart. Retail keeps it in the DB
    (`_STRG_RESTORE_SOLDITEM_*`, OPEN).
  - `Buyback` removes the entry, takes unit x count, and adds the item back with its instance.
    It puts the entry back and refunds if the bag is full.
  - New opcodes (OURS): 0x0118 list request, 0x0119 list, 0x011A buy back, 0x011B result.
- **Refusals** go to the system channel. The texts are the client's own:
  `UIIT_MSG_STRGERR_NOT_ENOUGH_GOLD` and `UIIT_MSG_ERROR_RE_BUY_OBJECT_CANT`, which
  SR_GameServer's `0x42aae0` refuses with. Which of our reasons maps to which is OURS.

## The deposit fee

- **The box (READ, round 726).** It shows max(1, ref +0xcc x max(1, count)).
- **The column (INFERRED).** Round 728 takes +0xcc as itemdata **column 30, KeepingFee**, from
  the `_RefObjCommon` schema name. Two checks support it: the real values look like fees (HP
  potion 1, X-Large HP potion 11, a starter sword 21), and the premium time items are 0, which
  matches the "1" in `MKtR5Kd.png`.
- **The data paths.** The column is added to:
  - refdata (`Item.KeepingFee`, the CSV column 72, the `items.keeping_fee` column, the export);
  - the client's `ItemTableReader` (GD and the native port, `keeping_fees`; an older native
    library reads 0).
- **The server charges what the box shows (INFERRED).** `storage.DepositFee` computes it;
  `Deposit` deducts the gold before the move and refunds if the move fails.
  - A purse short of the fee refuses with "not enough gold". The client shows
    `UIIT_MSG_STRGERR_NOT_ENOUGH_GOLD` (0x180f; SR_GameServer 0x524160's refusal).
  - The purse is re-read after a deposit.
