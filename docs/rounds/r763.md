# Round 763: EquipFx's effect masters simulated in Rust

Round 762 put weapon and seal particles back on every player within 720 units, as retail draws
them. That cost about 4 ms of EquipFx a frame, from about 50 effect masters (`EfpSim`) stepped in
GDScript, and round 761 measured that GDScript barely scales across threads (0.4-1.4x on 5). This
round moves the masters' per-frame simulation, the batch with its ordered particle cap, and what
they draw (the MultiMesh buffers and the Link strips) into the Rust GDExtension, on a Rust thread
pool, with the GDScript kept as the fallback and held to it bit for bit.

Based on dev `b52bc9dc` (v0.1.515, Godot 4.7.2). Labels: **READ** (Godot 4.7.2-stable's source,
fetched for reading; our code), **MEASURED** (the render box 192.168.10.78: RX 7600 RADV, 28
threads, Godot 4.7.2 editor build, `RENDER_DIR=/opt/opensro-client-r763`; crowd boots at 1920 x
1080 Forward+ through `xwl_run.sh`, under the shared lock), **OURS**, **OPEN**.

## 1. What moved, and what stayed (OURS unless marked)

| Piece | GDScript (kept, the fallback) | Rust |
|---|---|---|
| one effect's frame: the deaths' flush, motion and the follow levels, every command family, the emission, the spawn, the aging, the kept effect; `growth_bounds`; `set_origin` / `shift` | `EfpSim` (`efp_sim.gd`) | `native/src/core/efp_sim.rs` |
| Godot's f32 vector / basis arithmetic and its random stream | the engine | `core/gdmath.rs` |
| the batch: round 761's ordered global cap, exactly | `EfpSimBatch.Job` on WorkerThreadPool | `core/efp_batch.rs` on `core/pool.rs` |
| a master's draw buffers (`_update_draws`) | per particle `set_instance_transform / color / custom_data` | `core/efp_out.rs`, built on the thread that stepped it; sent by `SrEfpSim.apply_draws` (one `multimesh_set_buffer` a node with particles) |
| a master's Link chains and strips (`gather_from`, `spline`, `pipe_turn`, `obj_ribbon`) | `EfpLinks` | `core/efp_out.rs`, `core/efp_links.rs` (the camera-free strips; a pipe drawn with the camera's side stays GDScript, from the native chains) |
| the binding | -- | `native/src/gd_efp.rs`: `SrEfpTemplate`, `SrEfpSim`, `SrEfpBatch` |
| the switch | `EfpSimNative extends EfpSim` (`client/scripts/efp/efp_sim_native.gd`), `EfpEffect.use_native_sim`, `EfpSimBatch.run` | |

- **Who uses it.** EquipFx's masters only (`EquipFx._make_master` -> `use_native_sim`, after
  `use_shared_turn`). Skills, auras, the world's ambient effects and a weapon's own world-space
  simulation stay `EfpSim`; they share `EfpSim.live_total` with the masters, so the cap counts
  everyone as before.
- **Plain data in and out.** The compiled `EfpSim.Template` is packed once into arrays
  (`EfpSimNative.pack_template`, cached on the template); a batch takes the sims, `live_total`, the
  limits, the kept flags and each one's camera rotation, and returns per sim its frames, its change
  and its counters. The particles live in Rust; `particle_list()` builds `EfpSim.Particle` objects
  for the QA log and tests. Nothing names a native class as a type (ClassDB lookups by name), so
  every script compiles without the library.
- **Threads.** A batch runs while the main thread waits for it, so the main thread works on it
  too; the pool's helpers sleep on a condition variable between batches. Default: `min(4, cores,
  threading/worker_pool/max_threads)` threads in all, the main thread included (OURS, the quad-core
  target; section 3.1 measured no gain past 4). `OPENSRO_EFP_THREADS=<n>` sets it,
  `OPENSRO_QA_EFP_THREADS=0` the main thread alone, `OPENSRO_EFP_NATIVE=0` the GDScript masters.
  The pool's threads are joined at the library's deinit.
- **The ordered cap, unchanged in meaning.** Effect i's spawn at its own change d is taken iff
  `base_i + d < limit_i` (round 761). An undecided spawn now waits on the job's condition variable,
  woken by every bound published as well as every effect finished (round 761's review, F1: a
  waiter used to look again only when an effect finished).
- **The draw buffers** are Godot's MultiMesh layout (rows and origin, colour, custom data: 20
  floats an instance), the instance count grown as `_update_draws` grows it. A master's MultiMesh
  gets `custom_aabb = DRAW_AABB` (the box its instances already cull by): `_multimesh_set_buffer`
  otherwise re-makes the box over every allocated instance and notifies every instance drawing it,
  the master and each of its 64 holders (READ, `renderer_rd/storage_rd/mesh_storage.cpp`
  2106-2151).
- **Its own interface number** (`SrEfpBatch.efp_api()` = `EfpSimNative.EFP_API` = 1): additive
  classes, so `NativeAssets.NATIVE_API` stays 5 and an older library keeps its readers and simply
  leaves the masters in GDScript. Boot logs one line, `EfpSimNative: native effect simulation
  ON|OFF (...)`, and the Shift+F3 panel shows it.

## 2. Parity: exact, bit for bit (MEASURED)

### 2.1 How the floats are matched (READ)

GDScript keeps a `float` in 64 bits and a Vector3 / Basis / Color / packed float in 32 (`real_t`).
The port keeps each value where GDScript keeps it and does Godot's own operations in Godot's order:
- `Basis * Basis` is `tdotx/y/z` (element (i, j) = m[0][j]a[i][0] + m[1][j]a[i][1] +
  m[2][j]a[i][2]), `Basis * Vector3` is three row dots, `inverse()` the cofactors over the
  determinant, `orthonormalized()` Gram-Schmidt over the columns, `get_rotation_quaternion()`
  orthonormalized again, flipped by `scale(-1,-1,-1)` on a negative determinant, then
  `get_quaternion()`; `Vector3.normalized()` zero for a non-finite or zero vector; `Vector3 *
  float` narrows the float first (Variant's evaluator calls the `real_t` operator); `maxf` / `minf`
  are `a > b ? a : b` / `a < b ? a : b` (READ, `core/math/*.h`, `core/typedefs.h`,
  `core/variant/variant_utility.cpp`). No fused multiply-add: Rust does not contract, and the
  engine's x86-64 builds have no FMA in their baseline.
- Multiplying by the identity is done, not skipped: it turns a -0.0 into +0.0 in GDScript too.
- The random stream is `RandomNumberGenerator`'s: pcg32 seeded as `RandomPCG::seed` does with
  `DEFAULT_INC`, and `randf()` = `ldexp((float)(rand() | 0x80000001), -32 - clz(first draw))`, 0 when
  the first draw is 0 (READ, `random_pcg.h`, `thirdparty/misc/pcg.cpp`). A master's stream starts
  from the seed GDScript's `randomize()` chose, so the native master is the GDScript master.
- `sin` / `cos` are the C library's, as the engine's are (glibc on the box; OPEN on Windows, where
  the DLL's mingw libm and the engine's runtime are different builds -- at worst a last-place
  difference in a cone's angle, which nothing compares there).
- **Two inputs where the GDScript differs between engine builds** are taken as the editor/debug
  build takes them (the reference the checks run on): a singular basis's `inverse()` comes back
  unchanged (`ERR_FAIL_COND(det == 0)` under MATH_CHECKS; a release template divides by zero), and
  `Basis.get_quaternion`'s `is_rotation` check only prints. No real master hit either in the
  parity runs below (counted: 0).
- A dead particle stays readable: GDScript's particles are RefCounted, so a child keeps its dead
  parent's frozen position and rotation. The arena counts each particle's references (the list,
  its children) and frees it at zero; an emitter whose owner died is dropped, and a stale
  generation makes a later write to it a no-op, as GDScript's write to the orphan is invisible.

**Natively the cap is no longer worth its cost**: 880 more particles (+63 %) cost 0.08 ms of
EquipFx, and the uncapped native frame is the capped GDScript one (frame and p50 within 0.2 ms,
p95 +0.4-0.6, the same as the capped native p95). The batch alone at 4,000 uncapped particles is
0.3 ms on four threads (3.1). The GPU's share grows a little with the particles (10.2 against 10.1
ms, overdraw); on a slower GPU that is what remains to pay.

The recommendation was to run the native masters uncapped and keep 2,000 for the GDScript
fallback (where no cap is 2.2 ms of frame and 2.7 ms of p95 at 4,000).

### 4.1 USER DECISION 2026-10-09: no cap when the Rust simulation is active

The user decided: **remove the cap entirely when the Rust simulation is active** (like the
original); keep 2,000 for the GDScript fallback. Built (OURS):
- **The native masters count apart.** `EfpSimNative.live_native` holds their particles;
  `EfpSim.live_total` holds the GDScript effects' only. So the 2,000 cap (and its `RESERVE` for
  the player's own effects) keeps meaning what it meant for skills, auras, the world's effects and
  the masters' own fallback, and thousands of native particles neither count against it nor are
  refused by it.
- **Their limit is unbounded** (`EfpSimNative.limit_native`: `UNBOUNDED` = 2^30 unless
  `OPENSRO_QA_EFP_CAP` names one, the QA switch of round 761). The ordered admission is unchanged
  and stays exact: with `limit - hi` far above any change, `admit` decides every spawn at once and
  nothing waits (the suite: 0 waits; 2^30 plus any sum of changes stays far inside i64).
- **Tests** (`efp_native_test`): the default limit is unbounded; the parity runs at 8 / 33 / 60
  hold both sides to the GDScript cap so it binds alike (as before); a new run at 60 effects with
  both sides uncapped -- up to 9,716 particles alive, 0 spawns waited -- is the main thread's,
  bit for bit, at 1 / 2 / 4 / 28 threads; and a GDScript effect beside 9,680 uncapped native
  particles behaves exactly as one alone (120 particles, 0 refused). `efp_native_parity.gd` runs
  both sides under the GDScript cap (or `--cap`), so its comparison is unchanged.
- `QA CROWD split`'s `fx_cap_live_calls` is now the particles alive in all (GDScript plus native).

## 8. OPEN

1. **The cap for native masters**: closed by the USER DECISION of 2026-10-09 (section 4.1). Left
   open: the GPU's share of the extra particles on a slower GPU than the box's (overdraw; 10.1 ->
   10.2 ms here).
2. **The 0.2-0.6 ms of p95** the native masters show at 4,000 offline on the box, where the GPU
   sets the frame (3.2): render-thread cost of the whole-buffer uploads, or the boots' noise.
   Uploading only the visible instances would need the RenderingServer's per-instance setters
   again (what the GDScript path pays for on the main thread) or a buffer sized to the
   particles each step.
3. **Windows**: the DLL builds, carries the classes and passes `check_native_library.sh`; no
   Windows machine ran it (as for every native piece, `docs/NATIVE_ON_WINDOWS.md`). Its `sin` /
   `cos` are mingw's: bit parity with a Windows engine build there is not measured.
4. **A release export template's GDScript** divides by zero on a singular basis where the editor's
   returns it unchanged (2.1); the native rule is the editor's. None of the real masters met one (0 in the parity runs).
5. **What is left of EquipFx** (1.5 ms): the driver's scan and the 64 holders' placement every
   frame (GDScript, about 1 ms), and the nearest weapon's own world-space simulation (GDScript
   `EfpSim`, `fx_effects` 0.2-0.7 ms). The same port would take the latter (it is an `EfpSim`
   with `set_origin` every frame, which the native sim has); the former is node work.
6. **Other effects** (skills, auras, the world's ambient effects) still simulate in GDScript; the
   native `EfpSim` covers them (placement, `set_origin`, `shift` are ported and held to the
   GDScript in the suite), but their draws are per effect and were not measured as a cost.
