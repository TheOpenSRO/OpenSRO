# Round 735, weapon glow lane B: other players see each other's plus

Spec: `docs/protocol/weapon_glow.md`, lane B. Server and client net only. Lane A (round 734) owns
the glow's drawing. Labels as in the spec: **READ** (decompile or disassembly), **MEASURED**,
**INFERRED**, **OURS**, **OPEN**.

## Retail layouts (READ, both binaries)

| Message | Layout | Server writer | Client reader |
|---|---|---|---|
| `0x3038` put on | u32 uid, u8 slot, u32 RefItemID, u8 plus (equipment only) | `s:0x4e9de2`: uid `[ebp+8]`, destination slot `[edi+4]`, then the item's vslot 294 at mode 2 -> `CInstanceItem::vslot_010` `s:0x42e230`: `FUN_004958c0(+0x28)` = RefItemID, then for equipment `(u8)(FUN_00846200 + OptLevel +0x2c)` | `FUN_008a9260`: Read 4, Read 1, Read 4 (into the same variable as the slot: the slot byte is overwritten), then Read 1 when `!(w&2) && (b&0x1c)==0xc && (b&0x60)==0x20`; redresses through `ResolveVisualSlotForItem` and `FUN_009daf70(…, ref, plus, 0)` |
| `0x3039` taken off | u32 uid, u8 slot, u32 RefItemID | `s:0x4e9d03` and `s:0x4e9f98`: uid `[ebp+8]`, source slot `[edi+3]`, RefItemID from the item's vslot 1 (`+4`) | `FUN_008a9560`: Read 4, Read 1, Read 4 |
| `0x3015` spawn, a PC's items | u8 inventory size, u8 count, per item u32 RefItemID + u8 plus (equipment only), then the avatar block | `CGObjPC::vslot_294` `s:0x4e5a10` mode 2 -> `GStorage::FUN_004b8ad0` -> each item's `CInstanceItem::vslot_010` mode 2 (same as `0x3038`) | `GlobalDataManager::FUN_009de2f0`, CICUser vslot 25 (vtable `0xde2e7c`, slot 25 found by walking the vtable in the exe) |

- **The plus is the effective plus**: OptLevel + the advanced elixir's sum, added in a byte
  (`s:0x846200` walks the attached elixirs and adds each one's `+0x2c`). Closes the server half of
  spec OPEN 2 and all of OPEN 3.
- **Which items** (READ, relabelled by the review): `FUN_00490390` tests the ITEM: `+0x84`
  `CGObj::IsEquip` (TypeID1 3, TypeID2 1), then `+0x454` (TypeID3 13, the avatars) or `+0x470`
  (TypeID3 14, the devil's spirit) or `ResolveEquipSlotForItem` 0..8. It gates the equip
  (`0x4e9de2`) and the type-0 unequip (`0x4e9f98`). The move-type-7 path's `0x3039` (`0x4e9d03`) is
  not gated and covers slots 0..12; OpenSRO has no such move. The send is `FUN_00484d90`, a
  region-scoped send from the mover's own object.
- **The client's slot byte:** `0x3038` ignores it (the RefItemID overwrites it; the slot comes from
  the item type); `0x3039` uses it (`FUN_009daf70(slot, 0, 0, 0)`). OpenSRO's client keys both by
  it, which is retail's behaviour for `0x3039` and the same slot for `0x3038`.
- **The mover is told too** (READ, the review): both handlers have an own-uid branch
  (`DAT_00eef5e8`) that updates the character window and preview.

## Server

- `EquippedSnapshot.Plus` (`equipment.go`), filled by `equippedItems` with
  `equipment.Equipped.EffectivePlus()` = `OptLevel + AdvElixir` in a byte.
- **The pluses tail** (`world.go`; OURS framing, retail content): a block per snapshot, u8 count,
  then u8 slot + u8 plus for each worn item with a plus. It is the last field:
  - `OpEntityEntered`: after the model. With no model a 0/0 model is written first, which every
    decoder reads as "no model" (`DecodeEntityEntered` now treats RefObjID 0 as none, as the
    client always did).
  - `OpEnterWorldResult` and `OpChangeZoneResult`: a u16 count equal to the list, one block per
    other, after the models tail, which it forces written (and with it the headings, Seated and
    Restored, as the round-689 trap requires).
  - Written only when some snapshot has a plus, so every other payload is byte for byte the old
    one. The trap is passed on in the comment: a later field must force this one written.
- **`equip_broadcast.go`**: `EquipBroadcast` with the retail layout, `broadcastWorn` (`0x3038`) and
  `broadcastUnworn` (`0x3039`).
  - uid = the low 32 bits of the character id (round 710's id decision).
  - slot = OpenSRO's `equipment.Slot`, which is retail's equip slot index.
  - plus written only when the item table says TypeID1 3 / TypeID2 1 (the type-word test), or when
    there is no table (only equipment can be worn).
  - Only slots 0..8 (`BroadcastSlotMax`, READ from `FUN_00490390`).
  - Receivers: everyone in the mover's zone, the mover included as retail (review fix 5); the
    mover's client skips its own uid, its window and preview already redrawn from its equipment
    result. The zone instead of retail's region is a DEPARTURE in scope (OpenSRO spawns players
    zone-wide).
- `EquipmentHandlerWithBroadcast(…, hub)` (main.go uses it): `0x3038` after a successful equip
  (a swap is one `0x3038`, as retail), `0x3039` after an unequip.
- **GM `/item worn <equip slot> plus N | adv N`** (OURS; retail changes no worn item's plus):
  changes a worn item's instance in place through the new `equipment.InstanceSetter` (both stores),
  and the session layer sends a `0x3038` of the item (`gm.Result.WornChanged`). The bag-slot
  `/item` is unchanged.

## Client

- `WorldNet.EntitySnapshot.pluses` (slot -> plus) and `plus_in(slot)`; `_decode_pluses` and
  `_decode_pluses_list` read the tails of all three messages.
- `EquipmentNet.OP_EQUIP_BROADCAST` / `OP_UNEQUIP_BROADCAST`, `decode_broadcast` (the plus's
  presence is read from the length: the server writes it by the client's own type rule).
- **The hook for lane A**: `NetClient.other_player_equipment_changed(uid, slot, ref_id, plus)`,
  emitted for every `0x3038` (`plus` = the effective plus) and `0x3039` (`plus` = -1). `uid` is the
  u32; `World3D._other_by_uid(uid)` finds the character id.
- `World3D`:
  - `_other_pluses[character_id]` = slot -> plus, from every snapshot (`_note_other_pluses`) and
    every broadcast; erased when the player leaves.
  - `_on_other_equipment_changed` updates `_other_equipped` and `_other_pluses` and calls
    `_redress_other`, which swaps the dressed skeleton inside the existing node (the plate, click
    body, position and facing stay), re-registers sounds and the stand / sit loop, and keeps a
    running gait running. A broadcast for a player still waiting in a zone change's arrival list
    updates the kept snapshot.
  - Logs: `World3D: player <id> spawns with slot <s> item <i> at +<p>` and
    `World3D: player <id> now wears slot <s> item <i> at +<p>`; `NetClient: 0x3038 uid … plus …`.
  - Keyed by the slot byte: retail's own rule for `0x3039`; for `0x3038` retail resolves the visual
    slot from the item type, which is the same slot for 0..8.
- `OPENSRO_QA_REEQUIP="<unequip tick>,<equip tick>"` (QA only): takes the weapon off and puts the
  same item back on through the real messages.

For lane A: when `_build_assembled_character` takes the pluses, pass
`_other_pluses[character_id]` from `_redress_other` and `snapshot.pluses` from the
`_spawn_or_update_other` callers (`_on_entity_entered`, `_spawn_result_others`).

observer). Bram wears his starting kit: weapon 3632 in slot 6.

checked. Frames were deleted; the logs are kept.
