4. **CrowdGpu's frame** (`g_flush` 6.0): `_push_groups` walked all 6,800 groups every frame to find

   seconds.

Not the cost: the packets (0.6 a frame, `net_dispatch` 0.6 ms, about 9 0xB021 a second at
0.16 ms each), the plates (batched since round 757), skeletons, the dressing once done.

## 3. Built (OURS unless marked)

### 3.1 One far group per mesh across light levels (`CrowdGpu._write_light`)

A character's object colour (round 706: the region's ShadowMap byte / 384 under it, READ) was a
material copy per level (`ObjectLight.with_object_color`), so a far body's level picked its twin
and its group. Now the body texture has a fifth texel, the body's object colour; a part drawn
with a level copy draws with its base's twin, and its instance carries a "lit" bit; the vertex
shader takes `object_color` from the texel for a lit part (`object.gdshaderinc` under
`CROWD_GPU`; a mod shader's `OD0_LINE` the same, `CrowdGpu.twin_code`). The value is the one the
level copy carries (`ObjectLight.object_color_of` / `object_color_at`: 1/1024 levels, the base's
own near 0.6), so the far pixels are unchanged. A level change while far rewrites the texel; a
ghost's light (`ghost_light`) the same, without re-making its parts.

### 3.2 One far group per mesh across glow rows (`CrowdGpu._glow_row`, `_glow_twin`)

A glow material is shared per (row, plain material, option texture) (EquipGlow, READ): an item
worn at ten pluses was ten twins. Now every glow material of an item on a layout is ONE twin --
keyed by the glow shader and every parameter but the row's -- and the row's values (c1, c2,
period, mul0, signed2x, uv speed) are a row of a small glow table (`crowd_glow`, 3 texels a row),
its index in the instance. `object.gdshaderinc`'s `srr_glow_row` is `srr_glow`'s arithmetic on
those values (crowd_gpu_test holds the two texts equal after the substitution). The option
texture too (`b67ffb39`): the swarm's glows use four (MEASURED: three 256 x 256, one 1024 x 1024,
so no Texture2DArray), held by every glow twin as samplers `crowd_glow_t0..3` with
`glow_texture`'s own hints; the row names its slot. A fifth stays its twin's own.

INSTANCE_CUSTOM.y now packs ((glow row + 1) x 512 + (Volume row + 1)) x 2 + lit, exactly in a
float (`CrowdGpu.pack_y`).

### 3.3 EquipFx's masters stepped on the pool (`EfpSimBatch`)

EquipFx keeps one simulated master per effect file (round 748). The masters no longer process
themselves: EquipFx steps those a shown weapon draws, `EfpEffect.step_pre` (placement) and
`step_post` (the draws) on the main thread, `step_sim` -- `EfpSim.advance`, pure data -- for
all of them at once on WorkerThreadPool, HeightBatch's pattern (round 757's review, F3: the
effects claimed one at a time under a Mutex by up to 4 pool tasks and the main thread, which
waits only for effects a helper started). The one shared write, the global particle cap
`EfpSim.live_total` (OURS, round 620), is deferred: each sim may add at most its share of what
the cap left at the batch's start, and hands its count back after. OURS: when the cap binds, the
room is shared evenly instead of first come, first served. `efp_sim_test` holds the cap, the
counts, and the pool's particles equal to the main thread's when there is room.
`OPENSRO_QA_EFP_THREADS=0` steps them on the main thread.

### 3.4 Smaller

- `_push_groups` walks the dirty groups only (`_dirty_groups`), and the instance count is kept
  as parts come and go (`g_flush` 6.0 -> 0.3 ms live).
- `collect()` frees at most 128 groups a call (`COLLECT_MAX`), and a layout's twins are a set,
  not an Array.
- The far groups' shared bounds are snapped outward to 64 units (`CrowdGpu.snap_box`,
  `1cc2f223`), so a crowd growing them by a body's width does not re-set every group's AABB
  (`stats.aabb_pushes` counts the pushes).
- `CharacterBlobs._scan_step` checks validity before `is`: a live crowd frees bodies between the
  group read and the pass (140 `SCRIPT ERROR: Left operand of 'is' is a previously freed
  instance` in one 12-minute live boot, MEASURED; 0 after).

## 6. Open, and the larger redesigns (with numbers)

- **The user's own spot.** The box's player stopped at (950, 757) and sees 4,335 of the 7,003
  bots; the user's (1002, 1229) sees more. Every per-body and per-group cost here scales with that
  (INFERRED). A run from the user's spot needs a walkable route there for the QA click-walk.
- **What is left of the frame** (live after, 26.6 ms): the render's CPU 7.6 ms for 2,856 draws;
  the effect masters 4-5 ms wall; physics 3.3 (1.6 steps); `g_scan` 1.4; `post_tail` 2.3 (not
  split); the GPU 16.7 ms at 1080p on the RX 7600, busy 68 %.
- **Fewer groups than meshes is a redesign** (numbers from 4.2): what remains is one group per
  (mesh, shader): 1,994 live for 1,678 meshes. A union twin of the plain and glow object shaders
  (the glow chosen per instance) would make it 1,678 (-316). Below one draw per distinct mesh
  needs the meshes merged: Godot 4.2's MultiMesh draws one mesh per call and exposes no
  multi-draw indirect, so it would be a per-layout vertex atlas read in the vertex shader, or
  impostors for the farthest bodies. At about 2.6 us of render CPU a draw (MEASURED: 19.8 ms for
  7,520), the 1,678 floor is about 4.4 ms.
- **The effect masters** are 29-36 a frame (50 files in view), about 15 ms of pool time a frame
  at 30 fps; on the main thread now the placement, the draws and the wait (4-7 ms). Fewer
  masters (a cap on files shown, OURS), a lower simulation rate far away, or the simulation in
  C++ would each cut it; all change what is drawn or are larger work.
- **Arrival spikes.** A bot arriving (0x3015) is a 13-44 ms frame, one leaving (0x3016) 6.6 ms
  (MEASURED live, both trees); the dressing tail draws waiting bodies near (4.4). Round 756's
  lane.
- **The release binary** ran the before scene at 57.8 ms against the editor build's 65.9 (one boot
  each, the release one with the sampler attached): the user's numbers are the release
  build's.
- `stats.aabb_pushes` counted 13 whole-crowd bound pushes in the live after boot (20 in the
  swarm lineup at 7,000); the before tree has no counter, so the snap's share of the arrival's
  lower `rs_setup` is not split from the fewer groups' (OPEN).
