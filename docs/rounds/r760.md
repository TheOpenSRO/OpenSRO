## 2. Blocker 2a: every Skeleton3D processed every frame

**READ (scene/3d/skeleton_3d.cpp, 4.7.2-stable).**

- `NOTIFICATION_ENTER_TREE` calls `setup_simulator()` (the deprecated compat path, compiled into
  the official builds), which adds an internal `PhysicalBoneSimulator3D` child -- a
  `SkeletonModifier3D` -- and `_process_changed()`, which turns the internal process on for the
  default `modifier_callback_mode_process` (Idle).
- `_find_modifiers()` walks every child, internal ones included (`get_child(i)`'s C++ default),
  so every skeleton has one modifier.
- Each frame's `NOTIFICATION_INTERNAL_PROCESS` -> `advance()` -> `_update_deferred(
  UPDATE_FLAG_MODIFIER)` queues a deferred `NOTIFICATION_UPDATE_SKELETON`, which backs up every
  bone, runs the (inactive) simulator, and restores them.

So 18,035 skeletons queued 18,035 deferred updates a frame; the spike's `post_flush` 0.25 -> 3.79
ms at 1000 players was this.

**The fix** (`Skeleton3DBuilder.no_physics_step`, applied to every skeleton `build_skeleton3d`
makes; templates' duplicates inherit it): `modifier_callback_mode_process` = Manual (2) when the
property exists. `_process_changed` then keeps the internal process off at every tree entry (a plain
`set_process_internal(false)` would be undone there). The client builds no `SkeletonModifier3D`
(grep: no IK, look-at or physical bones; MapAnimation's AnimationPlayer sets poses, it is not a
modifier), so nothing needs the per-frame advance. A posed skeleton still updates:
`set_bone_pose_*` -> `_make_dirty` -> the same deferred update, which writes the skin and emits
`skeleton_updated` for the BoneAttachment3Ds.

**MEASURED** (`tools/skeleton_process_bench.gd`, headless, 18,035 duplicates of a 49-bone
template; wall ms a frame):

| | 4.7.2 | 4.2.2 |
|---|---|---|
| as built | 38.66; 39.07 (process callbacks 2.5) | 6.92 (physics callbacks 5.6 a step) |
| round 757's `no_physics_step` | 35.68; 35.22 | 6.87 |
| internal process off by hand | 6.87 | 6.89 |
| **round 760's `no_physics_step`** (0 of 18,035 still process) | **6.88; 6.87** | 6.87 |
| ... with 100 posed every frame | 6.90 | 6.90 |

After the bench's own fix (its posed check read poses never reset to rest): **0 of 100** posed attachments off their bone, 6.90 ms (MEASURED, 4.7.2).

`assets/skeleton_process_test.gd` (new): a built skeleton's duplicate has neither callback, keeps
them off across a re-entry, runs no skeleton update in 5 unposed frames, and a pose moves its
attachment with exactly one update; an untouched 4.7.2 skeleton does process (the probe). The
crowd census confirms it in the game: no `Skeleton3D` in "processing nodes by class" at 1000-7000.

## 3. Blocker 2c: the deadlock, and PoolWait

**READ (4.7.2-stable).** `servers/server_wrap_mt_common.h`: a RenderingServer call from a thread
other than the server's (`Thread::get_caller_id() != server_thread`) is queued; one that returns a
value or must be synchronous waits for it (`command_queue.push_and_ret` / `push_and_sync`; e.g.
`get_shader_parameter_list`, `material_get_param`, mesh and texture reads). With the default thread
model the server's thread is the main thread, which runs the queue only at its own RenderingServer
calls (`flush_if_pending`) and sync points. `WorkerThreadPool::wait_for_task_completion` from a
thread outside the pool blocks on the task's semaphore (`core/object/worker_thread_pool.cpp`). So a
task waiting for the main thread, and the main thread waiting for the task, wait for ever. 4.2.2
queued nothing (its pool-thread calls ran directly or failed thread guards), so no 4.2.2 run could
show it.

**The fix (OURS): `PoolWait.task(id)` / `PoolWait.group(id)`.** On the main thread it polls the
task and runs `RenderingServer.force_sync()` between polls (`command_queue.flush_all()` there; with
the separate render thread it waits for that thread, which serves the workers itself), then waits
for the finished task. Every main-thread wait in the client goes through it (35 sites in 14 files:
the template tasks, the cell prepares and their drop at a zone change, monster templates, effect
preloads, tables, audio, the title plan, the teardowns). A plain wait stays only where the task
cannot meet the RenderingServer, with a `# pool-wait: <reason>` note: HeightBatch's and round 759's
EfpSimBatch's helpers (NavGraph / EfpSim data only; their main-thread spin waits only for items a
helper already started). `pool_wait_lint_test.gd` holds it (a detector self-check of 4 banned and 5
allowed forms; the tree scan; the cell and template waits named).

The steady-state paths were already non-blocking (each polls `is_task_completed` before it waits);
the blocking waits that remain are the world's synchronous entry load, a zone change's drop of
cells in flight, the synchronous template path, and the teardowns -- and none of them can hang now.

**MEASURED** (`tools/pool_wait_probe.gd`: 6 pool tasks x 20 builds a round -- ArrayMesh,
ImageTexture, ShaderMaterial on a compiled Shader with its uniform list read back,
StandardMaterial3D, Skeleton3D, each duplicated on the worker -- the main thread waiting at once,
then building the same, then all drawn; 30 rounds; time limit 150-240 s):

| renderer, render thread | plain wait | PoolWait |
|---|---|---|
| Forward+, default | **hung 3 of 3** (rc 124 at round 0) | finished 4 of 4 (1.5 s) |
| Forward+, separate | finished 2 of 2 (1.4 s) | finished 2 of 2 (1.4 s) |
| Compatibility, default | **hung 2 of 2** | finished 2 of 2 (1.0-1.2 s) |

(The spike's probe saw Compatibility finish: it did not read the uniform list on the worker.)

## 5. Blocker 1: Compatibility

**The colour (READ, MEASURED).** Two engine changes the client's shaders did not follow:

1. **The cloud layer over the far scenery.** Round 754 pinned the cloud dome's vertices at clip
   `z = 0` for the reversed depth of 4.3+. That is Vulkan's far plane (RenderingDevice remaps z to
   0..1, reversed); GL Compatibility keeps OpenGL's -1..1 reversed (`core/math/projection.cpp`
   `set_depth_correction`, called with `p_remap_z` false by `rasterizer_scene_gles3.cpp` l. 890 and
   1540), where `z = 0` is window depth 0.5 -- in front of everything past a few units. The clouds
   were drawn over the far scenery (MEASURED: the Jangan palace washed out, +15.6 luma over the
   frame's top eighth). Fix: `WorldFog.far_clip_z(compatibility)` -- 1 before 4.3, 0 under Forward+,
   -1 under Compatibility -- into `cloud_dome.gdshader` (`p.z = far_clip_z * p.w`).
   `world_fog_test` checks a far-plane point lands on it after each renderer's own correction.
2. **DXT1 alpha under GL from 4.6.** GLES3 uploads `FORMAT_DXT1` as `COMPRESSED_RGB_S3TC_DXT1` from
   4.6 (RGBA at 4.2.2-4.5; `drivers/gles3/storage/texture_storage.cpp`), so a three-colour block's
   transparent texel draws opaque black, as Forward+ did before round 695 (MEASURED: the Jangan
   balustrade openings black, 1.2 % of the frame). Fix: `DdjReader.dxt1_needs_alpha_format` decodes
   those textures to RGBA8 under Compatibility on 4.6+ too, as under Forward+ (round 695's rule).

## 6. Blocker 3: the heap corruption (`table_parity.gd`)

**READ (core/string/ustring.cpp, 4.7.2-stable):**

1. `String::append_utf16` (behind `get_string_from_utf16`) counts the characters in one pass and
   writes them in a second. The first counts an unpaired lead surrogate as a character
   (l. 2053-2072); the second drops it when a plain character follows (l. 2098-2113). The string is
   one character longer than what is written: its last character is uninitialised heap. 4.2.2 does
   the same (round 671's "Invalid unicode codepoint (6db3bc40)").
2. Encoding such a garbage character overflows the heap: `utf8()` sizes a codepoint above
   0x7FFFFFFF as 1 byte and writes 3 (l. 1951-1953 against 2001-2006); `utf16()` sizes one above
   0x10FFFF as 1 unit and writes 2 (l. 2148-2150 against 2172-2175). Any print, `var_to_bytes`,
   `to_utf8_buffer`, or a GString handed to the native library triggers it.

`table_parity.gd` decoded the tables the native port hands back (the encrypted
`skilldata_*enc.txt`, also `regioncode.txt`, `effectsound.txt`, `fileinfo.txt` ...) as text and
passed cells to `SrNativeTables.numbers`, whose `to_string()` runs the engine's UTF-8 encoder. Not
our Rust and not the binding: the game's own readers decoded such tables the same way, so the
game's path was reachable too.

**MEASURED minimal repro** (`tools/utf16_garbage_probe.gd`, no native code): `FF FE 'A' D800 'B'`
decoded 200,000 times gives length 3 with 3 garbage characters each time; adding
`to_utf8_buffer` / `to_utf16_buffer` aborts with `corrupted size vs. prev_size` (rc 134); with
`--safe=1` (TextDecode) 0 garbage in 200,000 rounds.

**Fix:** `TextDecode.utf16(data)` (new) replaces every unpaired surrogate, lead or trail, with
U+FFFD before the engine decodes (eight `PackedByteArray.find` scans, no per-unit loop); plain text
decodes identically (BOM, byte swap, the stop at the first NUL). Every bare `get_string_from_utf16`
in the client goes through it -- 27 game sites, 5 tools (`utf16_garbage_probe` keeps a bare one as
its negative) -- and `text_decode_lint_test.gd` holds it. No Rust change: `tables.rs` already hands
such tables back.

**MEASURED:** `table_parity.gd` with the decodes reverted: rc 134 `double free or corruption
(!prev)`, 2 of 2. After: **`TABLE PARITY PASS` 3 of 3** (70-72 s; 261 "handed back" lines, 84 of
them `*enc*`). `native_parity.gd` PARITY PASS. `cargo test` 45 passed. `text_decode_test.gd`: 8
plain shapes identical to the engine, 8 unpaired cases U+FFFD, 300 random encrypted-like tables
decode deterministically and encode cleanly, the exact parity path 2,000 times with the library;
its negative (the bare decode put back on a box copy) fails 8 checks and then aborts. Cost: 670
Media.pk2 tables (200 MB) decode in 783-799 ms against the engine's 371-386 (about +2 ms a MB, only
where the GDScript readers run).

### 14.1 The text at UI scale 2.0 (the user's RTX 5080 test)

The user's 4.7.2 build at UI scale 2.0 drew text heavier than 4.2.2: the tooltip's bold lines, thicker
dark edges, the name plates "rasterised small and scaled up". Two causes, both oversampling (READ,
`modules/text_server_adv` and `scene/3d/label_3d.cpp` at 4.2.2- and 4.7.2-stable):

1. **Emboldened faces.** 4.2.2 had one global oversampling, and FreeType's embolden stroke was
   `embolden x size x 4` (26.6) of the UNSCALED size, rasterised at size x oversampling: on screen,
   stroke / oversampling. 4.7.2 oversamples per viewport and keys the glyph by `size x 64 x
   oversampling`, so the stroke `embolden x key / 16` keeps its full width: at 2.0 the tooltip's bold
   (embolden 1.4) and the chat's (0.6) were twice 4.2.2's.
2. **Label3D.** 4.2.2's global oversampling reached the 3D labels (glyphs at size x oversampling,
   metrics / oversampling). 4.7.2's viewport oversampling is applied only by a CanvasItem's glyph
   draw, so a Label3D is a 1x raster; the monster plates, which grow with the UI scale, were that
   raster magnified 2x.

oversampling (tooltip, chat); every Label3D the client makes (plates, monster plates and boxes,
floating numbers) gets 4.2.2's raster -- font and outline size x oversampling, `pixel_size` /
oversampling (the quad on screen unchanged; NamePlateBatch reads the label, so the batched plates
follow). Re-applied when the UI scale changes. Nothing changes at scale 1 or before 4.5.
`font_oversampling_test`. `OPENSRO_QA_FONT_OVERSAMPLING=0` is the QA before-switch.
