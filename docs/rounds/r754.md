# Round 754: spike -- the client on Godot 4.7.2

The user's choice: try the upgrade from Godot 4.2.2 to 4.7.2. **A spike:** the branch
`spike/r754-godot-4.7`, nothing merged, nothing shipped, every 4.2.2 workaround left in place.

Based on `b7b89bed` (dev, v0.1.511). Labels: READ (engine source or docs at the named tag),
MEASURED (run on the render box, 192.168.10.78, RX 7600, RADV / radeonsi), OURS (a decision of this
project), OPEN.

## Verdict

**Upgrade -- after three things.** On Forward+ (what players run) 4.7.2 is the same picture and
faster everywhere it was gated: frames -21 to -27 % at the Jangan spawn, the Dunhuang reeds and the
region crossing, entries -6 to -9 %, the longest freezes -6 to -7 %, none slower (section 6). The
port is small and done in this branch (section 3: 14 items, the suites 258 of 258 on 4.7.2 and
still on 4.2.2), the native readers load either way and agree with the GDScript readers on the
real archives (section 4), and three of the hardest 4.2.2 workarounds are gone (the const-array
race, the lambda null self, `Node.duplicate()` off-thread; section 5). Above all, the threading
round 757 needs only works on 4.7.2: 4.2.2 crashes with the separate render thread, 4.7.2 runs
1000 players standing at 15.0 ms against 4.2.2's 17.5 (section 7).

Before it ships:

1. **Compatibility** (section 8 and 6): +6 to +12 luma in sunlit views and a frame 17 % slower at
   Jangan; find the colour change and match it, and look at the cost.
2. **The render thread with a crowd** (section 7): the default thread is 4 ms slower than 4.2.2 at
   1000-3000 players, and deadlocks Forward+ if the main thread waits on pool tasks that make
   rendering resources (section 5). Either ship the separate render thread (fastest measured, but
   Godot itself still calls it experimental: it needs a long soak on Windows and the Steam
   Machine), or find the deferred-update cost.
3. **The 4.7.2 heap corruption** in `table_parity.gd` (section 4): isolate it, or show the game
   never takes that path.

Then the user's own test of the spike build (section 10) on the Steam Machine, and the Windows
build on a Windows machine, which nobody here has run.

## 1. The version

- **4.7.2-stable exists.** GitHub `godotengine/godot`, tag `4.7.2-stable`, published 2026-08-18; a
  maintenance release ("no known incompatibilities" with 4.7.1; 57 fixes). It is the newest stable
  4.x (4.7 2026-06-18, 4.7.1 2026-07-14). Release notes:
  https://godotengine.org/article/maintenance-release-godot-4-7-2/ ; changelog
  https://github.com/godotengine/godot/blob/4.7.2-stable/CHANGELOG.md .
- **On the box, side by side** (never replacing 4.2.2): `/opt/godot-bin/Godot_v4.7.2-stable_linux.x86_64`
  (SHA-512 of the zip checked against the release's `SHA512-SUMS.txt`), and its Linux and Windows
  templates (plus `icudt_godot.dat`) in `~ghidra/.local/share/godot/export_templates/4.7.2.stable/`
  (`.tpz` SHA-512 checked). `4.2.2.stable` and the 4.2.2 binary are untouched.
- The migration notes 4.2 -> 4.3 -> ... -> 4.7 were read (godot-docs `upgrading_to_godot_4.x`),
  with the changelogs; what bit this project is in section 3, what did not at its end.

## 2. The tools: another binary by name

`GODOT_BIN` (OURS) picks the box binary in `remote_godot.sh`, `qa_shot.sh`, `crowd_run.sh`,
`check_scripts.sh`, `renderer_fallback_box_test.sh` and `retail_bloom_box_test.sh`; unset, every
tool runs 4.2.2 exactly as before. `perf_gate.sh` runs `GODOT_BIN` on both sides, or
`BASE_GODOT_BIN` on the base side only (a base on another binary gets its own shared copy and cache,
`-g472` suffixed, so a 4.2.2 base copy is never re-imported by 4.7.2), and `PERF_BOX_LOCK` takes a
box lock around each run. This lane ran under `RENDER_DIR=/opt/opensro-client-g47` and
`GODOT_LOCK=/var/tmp/g47/lock` (the 4.2.2 side under `/opt/opensro-client-g42`). Also:

- **qa_shot's reap** kills every `godot-bin/Godot_v4.` binary (it matched 4.2.2 only), and
  `re_tick.sh` stands down for any; `crowd_run.sh` counts any 4.x as "another lane's Godot".
- **The renderer banner changed** (MEASURED): 4.7.2 prints `Vulkan 1.4.305 - Forward+ - Using
  Device #0: ...` where 4.2.2 printed `Vulkan API 1.4.305 - Forward+ - Using Vulkan Device #0: ...`.
  The perf gate read the renderer from that line and would have failed every 4.7.2 run; the five
  tools now match `^(Vulkan|OpenGL)( API)? [0-9]`.
- **The movie size (4.6+).** `--write-movie` sizes the movie from the project's window settings,
  not from `--resolution` (READ, `main/main.cpp` 4.7.2: `movie_size = Size2i(GLOBAL_GET(
  "display/window/size/viewport_width"), ...)` then `window_width/height_override`; absent in 4.5,
  present from 4.6). Every 4.7.2 `qa_shot` frame came out 1152 x 648 for `--size 1280x720`
  (MEASURED). Under 4.6+ qa_shot now writes the size as `window_width/height_override` into the
  client copy's `override.cfg` for the run and puts the copy's own file back after.
- `check_release_zip.sh` accepts any `GODOT ENGINE 4.x` notice (it required `4.2.2`).

## 4. The native readers

- **Binding:** godot-rust `godot` crate `=0.5.5` (the newest; `api-4-7` exists from 0.5.4). Built
  with `api-4-2` (as shipped) and with `api-4-7` (the spike's `Cargo.toml`); the spike's
  `.gdextension` says `compatibility_minimum = 4.7`.
- **Both load on 4.7.2** (MEASURED): the shipped `api-4-2` library -> `native readers ON`; the
  `api-4-7` one -> ON, `native_assets_test` ALL PASS. 4.2.2 refuses the `api-4-7` library
  ("GDExtension only compatible with Godot version 4.7.0 or later") and falls back to GDScript, as
  designed. The GDScript fallback loads on 4.7.2 (every suite ran without the library first).
- **Parity on the real archives, 4.7.2 + api-4-7** (MEASURED): `native_parity.gd` PARITY PASS (4
  archives: trees, 94,498 lookups, 53,083 files / 3.0 GB read, 10,877 per-pixel decodes);
  `native_parity_models.gd` PARITY PASS (25,252 .bms, 5,235 .ban, 1,251 .bsk, bit for bit);
  `table_parity.gd` 13 FAIL before port #11 (the `E` exponent, the run that completed). **After it,
  no run completed: 4.7.2 aborts inside the tool with heap corruption** (`free(): invalid pointer`
  / `free(): invalid next size`), every time right after the tool decoded an *encrypted* table
  (`skilldata_*enc.txt`) as UTF-16 text -- bytes that are no text, full of unpaired surrogates --
  and hands it to the GDScript readers (`TABLES handed back ... unpaired UTF-16 surrogate`). It is
  the engine, not the binding: 4.7.2 with the shipped **api-4-2** library aborts the same way 3 of
  3, 4.7.2 with api-4-7 2 of 3, and **4.2.2 with the api-4-2 library passes 3 of 3** (MEASURED).
  A random-bytes probe of the same calls (decode, split, re-encode) did not reproduce it in 300
  rounds; a larger one was stopped to free the box. The game's readers decrypt those tables
  before reading them as text, so the game may never take that path, but where 4.7.2 corrupts
  its heap is not found: OPEN (risk 3).
- The release library still links against glibc 2.28 (zig), and 4.7.2's own Linux binary and
  templates still need only `GLIBC_2.28` (MEASURED, `objdump -T`), so the floor holds.

None was removed (a spike). MEASURED ones ran as small probes on the box, both binaries.

|---|---|---|
| **const Array read race** (r748 F1; `const_array_lint_test`, 25 `static var`s) | **not needed** | READ: `Array::operator[] const` no longer hands elements through the shared `read_only` slot from 4.5 (`core/variant/array.cpp`; the VM's `for` and indexed reads use it). MEASURED (`constrace` probe: two pool tasks + the main thread, 8 s, for/index/front on one const Array of Strings): **4.2.2 22.4M-35.8M wrong reads per run (4 runs); 4.7.2 0 wrong reads (4 runs)**, and 4.7.2 ran ~50 % more loops |

**For round 757 (threading):**

- (a) the const-array race is gone on 4.7.2 (0 wrong reads against tens of millions);
- (b) `Node.duplicate()` and node/resource creation on pool threads work on 4.7.2 and do not on
  4.2.2 -- **but with the default (safe) render thread, building rendering resources on pool
  threads while the main thread waits for the tasks deadlocks Forward+ on 4.7.2**: either keep the
  main thread pumping (no `wait_for_task_completion` while workers make RIDs) or run the separate
  render thread;
- (c) the separate render thread (`thread_model=2`) at 1000 and 3000 other players (section 7):
  **4.2.2 crashes (SIGSEGV) right after the world loads, both times; 4.7.2 runs and is the fastest
  configuration measured** -- 15.0 ms standing at 1000 (4.2.2's default 17.5, 4.7.2's default 21.8),
  35.7 at 3000 (40.9 / 44.7), walking 19.6 at 1000 (28.5 / 29.7).

So the threading work belongs on 4.7.2, and on 4.7.2 it needs the separate render thread (or no
main-thread waits on RID-making tasks).

## 11. Risks

1. **Compatibility is brighter and slower** (+6 to +12 mean luma in sunlit views, section 8; the
   Jangan frame +17 %, section 6), cause not found. The Compatibility launcher's players would see
   a different picture.
2. **The default render thread is slower with a crowd** (+4 ms at 1000 and 3000 standing,
   section 7) and **deadlocks Forward+ when the main thread waits on pool tasks that make
   rendering resources** (section 5). The separate render thread fixes both on the box, but Godot
   4.7.2 itself calls it experimental ("can lead to project crashes or instability") and it was run
   in 2 crowd boots and 3 probe runs only -- not on Windows, not on the Steam Machine, not for hours.
3. **Heap corruption in 4.7.2** while the GDScript readers take an encrypted table's garbage
   UTF-16 text (`table_parity.gd`; 4.2.2 clean). Not isolated; the game may not take the path.
4. **Same-frame reads of a BoneAttachment3D lag a frame** (port #2): EquipFx places a near
   weapon's particles from the attachment in `_process`, so on 4.7.2 they trail their weapon by one
   frame (the far crowd computes its own frame and is unaffected).
5. **The quit fix is coverage, not a rule.** Every un-waited WorkerThreadPool task aborts 4.7.2 at
   quit; the holders found (port #12) were found by quitting the world on two renderers and the
   empty world. A path not quit from here (a reconnect, a zone change, the front end, a party
   window) may still hold one. A lint like `const_array_lint_test` (every `add_task` paired with a
   wait on the owner's teardown) would make it a rule.
6. **Log formats changed**: floats print as `1.0` (port #7) and the renderer banner reads
   differently (section 2). Tools that parse logs beyond those fixed here may miss lines.
7. **Data reads differ**: `is_valid_float` takes `2.9999999E-2` (port #11), so npcpos cells that
   read 0 on 4.2.2 now read their value.
8. **The branch drifts.** 680 `.uid` files and 4.4+ project changes; every script another lane adds
   on 4.2.2 arrives without its `.uid` and gets one on the next 4.7 import. The port is small
   enough to redo on a later dev, and its script changes run on 4.2.2 as well (258 suites), so they
   can land ahead of the engine switch (not the `.gdextension` floor, `config/features` or the
   `api-4-7` binding).
9. **Not tested:** Windows (no Windows machine here; the zip only passed the static checks), the
   Vulkan-less fall-back (`vk_fallback.rs` against 4.4's own `fallback_to_opengl3`), a session
   against a live server, hours of play, and the user's Steam Machine (the spike zip is for that).
   4.5+ also needs SSE4.2 and Windows 10 or later.
10. **Lineup and select-screen parity unsettled** (section 8): no same-version noise floor.
