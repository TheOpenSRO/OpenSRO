# Round 740, weapon glow: inheritance through OrgObjCodeName, and itemrare.txt

A bug in round 734: `ItemGlowTables` keyed the glow types and particles by code name only, with no
inheritance. Spec: `docs/protocol/weapon_glow.md` §1.4 and §1.5 (new). Labels: **READ** (decompile or
disassembly), **MEASURED**, **INFERRED**, **OURS**, **OPEN**.

## The reading (READ)

The brief's reading of `UI_ALCHEMYBOX::FUN_00a9f2e0` is **verified**, with two details made exact:

1. The item walk (0xa9f388..0xa9f65a). `FUN_008cb810` returns `mgr+600`, a `std::map`: node +0xc is
   the RefID, +0x10 the record, and `FUN_00973420` gives its RefObjCommon block (+0x10). CodeName
   (+0x08) → RefID goes into a local map with an insert. The type-word gate (asm 0xa9f45b..0xa9f4d7)
   is `!(w&2) && (b&0x1c)==0xc && (b&0x60)==0x20`, then `(w&0x780)==0x300`, or `==0x200` with
   `w>>11` equal to 1 or 2. A passing item whose OrgObjCodeName (+0x40) has a non-zero length
   (`cmp [eax+0x14],ebx` at 0xa9f4e7, i.e. +0x54) has its RefID pushed onto a vector in a second map,
   OrgObjCodeName → vector of RefIDs. **`xxx` never reaches that test as text**: the wide reader stores
   it as "" (`characterdata.md`), so an Org of `xxx` joins no group. It does not form an "xxx" group
   that resolves to nothing.
2. `itemoption.txt`: code name → RefID → `DAT_0110ac80` (`FUN_00452230`, an insert).
3. The groups, in key order (a `std::map` keyed by the wide string): the key as a code name → RefID →
   its entry in `DAT_0110ac80` (`FUN_004522f0` at 0xa9f9d3). If found, each vector RefID not yet in
   the map is inserted with that type (0xa9fb04). Because it runs in key order and checks the map as it
   stands, a group sees types given by groups before it. A chain (A's Org is B, B's Org is C) works
   only if B's key sorts after C's. The archive has no chain (MEASURED, below).

**The particle table has the same inheritance, and a second source file.** It is not loaded inside
`FUN_00a9f2e0` (round 734's §1.3 said so) or through `FUN_00a9a050` (which appends a glow row). It is
loaded by its own function, `UI_ALCHEMYBOX::FUN_00aa0270(path)`. `Client_LoadAllRefData` calls it
twice (asm 0x846755..0x84676e) after `FUN_00a9f2e0`: **`push 0xdd30f8` = `resinfo\itemrare.txt`**,
then `push 0xdd30dc` = `resinfo\itemoptionefp.txt`. Both calls fill `DAT_0110ac98`:

- The item walk and the gate are the same (`call 0x8cb810` at 0xaa031f; the gate is the
  same five tests, read in its decompile).
- A row's list is made on the item's first row (0xaa089b allocates the vector; `FUN_00a8f5c0` puts it
  in `DAT_0110ac98` and in `0x110aca4`, the owner list). If the item already has a list, the row goes
  into the list it already has (0xaa090f reads the map's value, and the append at 0xaa0ae0 goes
  through that pointer, `mov ecx,[esp+0x38]`).
- The groups step inserts the **base's vector pointer** for each member that has none (0xaa0cf1), and
  `0x110aca4` is not touched. So a member shares its base's list, and a member that inherited at the
  `itemrare.txt` call adds its own `itemoptionefp.txt` rows to that shared list.
- `CObjCharacter::FUN_00a5f3e0` runs the particle loop whatever the plus. Only the glow lookup is
  inside `if (plus != 0)`. So `itemrare.txt`'s rows, which have no min/max columns (0..0xFF), show
  at +0.

## Built

- `ItemTableReader.Item.org_code_name`: column 4, stripped, `xxx` (any case) → "", the same as
  `parse_org_codes`. Read on the GDScript path and by the native reader (`native/src/core/tables.rs`
  `org_code_names`, `gd_tables.rs`). A library built before this round lacks the column, so it gives ""
  and nothing inherits. `cargo test` passes for the tables (10/10). `native_tables_test.gd` compares
  the field both ways and checks `xxx`/missing.
- `ItemGlowTables`:
  - `RARE_PATH`, loaded before `EFP_PATH`. `load_particles` is one call of the client's loader, and
    its rows are kept per call.
  - `inherits_glow(cash, bionic, type_ids)` packs the type word and runs the client's tests as
    written.
  - `inherit(items)` adds the groups of new members and rebuilds `_types` from `itemoption.txt`'s own
    types (`_direct_types`), then rebuilds `_particles` call by call, with members sharing the base's
    `Array`. A partial table and then a fuller one end where the fuller one alone would.
  - The keys stay upper-case code names (OURS; no collisions, MEASURED).
- `CharacterAppearance`: the glow tables are set before `add_item_rows`, and both `add_item_rows` and
  `_item_info`'s full load call `glow_tables.inherit(rows)`.
- `client/tools/glow_inherit_probe.gd`: the measurement above, through the client's own code.

## OPEN

- Whether the client compares code names with case (the `std::map<wstring>` is case-sensitive; OpenSRO
  upper-cases). This makes no difference on this archive (no collisions), but a table whose case
  differed from the item's would resolve here and not in retail.
- `FUN_004f1840` / `FUN_00452230` / `FUN_00a8f5c0` are taken to be `std::map::insert` (first value
  wins) from their call shape (INFERRED). `itemoption.txt` has no duplicate code (MEASURED), so this
  makes no difference here. OpenSRO's `load_options` keeps the last value, as before.
