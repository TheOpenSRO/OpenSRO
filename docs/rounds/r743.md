## What was racy, and the proof

Every test below is a deterministic race. The test holds the contested row's lock from a third
connection (`testdb.HoldRow`), starts both racers, waits until Postgres reports both blocked
(`testdb.WaitLockWaiters`, from `pg_stat_activity`), and then lets go. So both racers have read
before either writes, on every run.

**Where the races happen in-process today.** The gateway runs one session's packets in order, so
two requests from one client never overlap. What overlaps:
- the two traders' handlers;
- two players picking up;
- an Item Auto Share credit landing in a member's bag while that member acts;
- two characters of one account at the warehouse;
- after M2, other processes.

## The fixes

### `internal/txn` (new): one action, one transaction

- **The transaction travels in the context.**
  - `Runner.Run(ctx, fn)` begins one transaction and gives `fn` a context carrying it.
  - Every SQL store reaches the database through `txn.Conn(ctx, db)`, or `txn.Begin(ctx, db)` for
    its own multi-statement steps. These are the stores converted: character, account, inventory
    (bag and warehouse), equipment. Inside an action, `Begin` is a **SAVEPOINT**, so a store's own
    all-or-nothing step stays all-or-nothing inside the larger one. A failed `PlaceItemInstance`
    inside a deposit rolls back to its savepoint, and the deposit carries on.
  - `fn`'s error rolls everything back. There is no refund or put-back code anywhere in the
    converted actions.
- **Retries.** A deadlock (40P01) or serialisation failure (40001) is retried, up to 4 attempts
  (OURS). `fn` touches only stores, so a rerun is safe.
- **In memory** (`-no-postgres` and most tests):
  - the in-memory stores register an undo for every change (`txn.OnRollback`), which `Run`
    replays newest first;
  - without a database, `Run` also serialises actions on one process-wide mutex.
- **`txn.For(stores...)`** picks the database of the first SQL store among an action's stores.
  The services need no new wiring: shop, storage, trade, pick-up and GM build their runner from
  the stores they already hold.
- **Per-owner write locks.** `txn.LockOwner` takes `pg_advisory_xact_lock(hash(table), owner)`.
  Every inventory write takes it for its owner, and equipment takes its own for the character
  (the lock order is equipment, then bag). Under it, rows are read `FOR UPDATE` and writes count
  their affected rows.
- **The ledger.**
  - The `economy_ops` table: `txn.Claim(ctx, key)` inserts `ON CONFLICT DO NOTHING` inside the
    action's transaction, and a second claim of the key answers `ErrAlreadyApplied`. This is the
    spec's `trade_log`, generalised.
  - `Runner.Applied` asks whether a key committed.
  - `PruneLedger` deletes rows older than a day, hourly (OURS).
- **Serials.** `item_serial_seq` numbers item rows and ground items. `txn.Serials` reserves 256 per
  round trip (OURS).

### Item serials

- **The tables.** `inventory_slots` and `account_storage_slots` carry `serial BIGINT NOT NULL
  DEFAULT nextval('item_serial_seq')`, with a unique index per table. The schema is live-safe and
  re-runnable: added nullable, backfilled, then the default, `NOT NULL` and the index.
  `inventory.TestSQLSerialBackfill` runs it on a legacy-shaped table twice.
- **Identity.** A whole stack taken by `TakeItem` carries its serial in `Instance.Serial`. A store
  that places it as a new row keeps it, so the item keeps its identity across a trade, the
  warehouse and a buy back. A part of a stack gets a new serial, and a merge absorbs it.
- **Uniqueness.** The unique index refuses the same serial written into one table twice.
  `inventory.TestSQLSerialFollowsTheWholeStack` covers it.
- **Not carried:**
  - **`equipment_slots` has no serial yet**, so an unequipped item takes a new one (OPEN);
  - **uniqueness across tables** (a serial in the bag and in the warehouse at once) is not
    enforced by an index. The ledger and the per-action transactions are what prevent it (OPEN:
    a registry table if M5 needs it).

### One pool (`cmd/server/main.go`)

- **The pools.** `txn.OpenPool` gives the stores one pool with `SetMaxOpenConns`. The account,
  character, inventory (twice), equipment, skill, guild, quest and friend stores now share it,
  through new `NewSQLStore(db)` constructors. Their `Close` leaves a shared pool open.
- **The budget.** `OPENSRO_PG_MAX_CONNS` is the process's whole budget: default 40, 32 for the
  stores and 8 for the reference data (OURS). A value under 4 is ignored.
- **Why the reference data has its own small pool.** An economy transaction holds a stores
  connection while it asks the reference data for a stack size or an item row. If that ask waited
  on the same capped pool, a full pool could deadlock against itself.
- **Before:** ten pools, none capped (spec 2.1). The `pgwait` ping pool is unchanged: one
  connection, closed.

## Behaviour that changes (server-internal; no message or layout changes)

- A confirm that arrives while the trade executes is answered OK, as before, and no longer runs
  the trade again. A cancel or a disconnect during the execution no longer ends it: the trade
  completes, and both sides get the usual result.
- A trade whose credit finds no room is cancelled ("no room") with nothing moved. Before, the item
  was destroyed and the handler errored.
- A gold pick-up split among a party is all or nothing. Before, failed shares were lost and the
  picker was still answered.

**One fix came out of the gates.** The first full session run failed three tests:
- `TestGoldPickUpTellsEveryShare`
- `TestTradeInsufficientGold`
- `TestTradeResentConfirmDuplicatesItem`

The cause was **ledger keys colliding between hubs of one process**. Trade ids and ground-item ids
were per `Hub`, and the tests make many hubs. So a later test's trade 1 or pile 1 found the key
an earlier test had claimed. Trade ids are now process-wide (`trade.tradeIDs`). A drop without a
serial source gets a negative process-wide number (`grounditem.localSerials`). In production there
is one hub of each, so this was a test-only collision. It is fixed at the source all the same.

## deploy/README.md

The new section, "Economy transactions, item serials and one connection pool (round 743)", has
three parts:
- **No manual step**: the schema is created at boot. Check queries follow.

  not touched.
- **The review's F9** (`-no-postgres` and tests only): the in-memory undo restores a whole bag
  snapshot, so a plain store call made between an action's write and its rollback (a potion's
  `RemoveItem`) is erased with it; and the in-memory ledger is never pruned. The fix is a per-slot
  journal and a pruned `memLedger`.
- **The review's F10**: a quest kill reward is two commits (`quests.RecordKill`, then `AddGold`,
  `session/combat.go`). A failure between them loses the reward; it cannot duplicate it. It joins
  the M1 follow-up list above.

  (the review's F8).
