# srrevamp server

The Go game server for srrevamp: a clean-room reimplementation of a Silkroad
Online–style server, written from what was recovered out of the original
binaries and the player's own client archives. It ships **no game data**: every
table it needs is generated by the operator from their own client (see
[Reference data](#reference-data)).

This file is guarded by a test (`internal/systems/readme_test.go`): every tool
under `cmd/` and every flag `cmd/server` registers must be mentioned here, or
`go test ./...` fails. When you add one, add it here in the same change.

## Build and run

```
go build ./... && go test -p 1 ./...                 # the real loop
go run ./cmd/server -in-memory -addr 127.0.0.1:15899 # no database, nothing persisted
go run ./cmd/server -postgres-dsn 'postgres://postgres:postgres@localhost:5432/srrevamp?sslmode=disable'
```

The production shape is the compose stack in the repo root (`docker-compose.yml`,
`deploy/`): Postgres plus the server, the server rebuilt from `origin/dev` by
`deploy/update.sh`. The public test server and its exact override are described
in `deploy/README.md` and `docs/HANDOFF_OPENSRO.md`.

## `cmd/server` flags

| flag | env default | what |
|---|---|---|
| `-addr` | — | listen address for the gateway (`:15779`) |
| `-postgres-dsn` | — | PostgreSQL DSN; the persisted store for accounts, characters, inventory, equipment, storage, guilds, friends, quests, skills, reference items/skills/drops |
| `-in-memory` | — | run with in-memory stores instead of PostgreSQL (QA renders, tests, local play; nothing survives a restart) |
| `-tls-cert` / `-tls-key` | — | serve TLS on the gateway instead of plain TCP |
| `-leveldata-csv` | `SRREVAMP_LEVELDATA_CSV` | the EXP curve (`export-leveldata`); **without it characters never level** |
| `-skills-csv` | `SRREVAMP_SKILLS_CSV` | skill reference data (`export-refdata`), in-memory mode; PostgreSQL imports it instead |
| `-items-csv` | `SRREVAMP_ITEMS_CSV` | item reference data (`export-refdata`), in-memory mode; PostgreSQL imports it instead |
| `-npcpos-csv` | `SRREVAMP_NPCPOS_CSV` | the game's monster placements (`export-refdata -mode npcpos` on a client's `npcpos.txt`); every roster species with rows stands where the game puts it, otherwise at its own-design anchor near the town |
| `-teleport-dir` | `SRREVAMP_TELEPORT_DIR` | the game's teleport network: a directory holding `teleportdata.csv`, `teleportlink.csv` and `teleportbuilding.csv` (`export-refdata -mode teleport` on a client's own `teleportdata.txt`, `teleportlink.txt` and `teleportbuilding.txt`). Loaded, joined and counted at boot (`level=INFO msg="teleport network loaded" dir=<dir> points=222 links=292 buildings=77` on a retail archive's export); a configured directory that does not load is fatal. Nothing uses it yet: the town teleporters' handler is the next item (round 575, `internal/teleport`) |
| `-gm-accounts` | `SRREVAMP_GM_ACCOUNTS` | comma-separated account usernames allowed to run the in-game GM commands (`/tp`, `/give`, `/level`, ...); case as stored in `accounts.username`; default none. Every command is logged with the account. See `docs/DEBUG_TOOLS.md` |
| `-monster-ai` | `SRREVAMP_MONSTER_AI` | **default off**, and the kill switch. On, the monster AI tick runs: monsters idle, wander at their walk speed, run home past a 200-unit roam radius (own design), and stand where a blow found them while any player in the zone has an auto-attack on them (round 539), each move pushed to the zone (`OpMonsterMoved`). Off, nothing moves and the wire is what it was. The env value is `strconv.ParseBool`'s (`1`, `true`, ...); anything else is off with a WARN. Needs a client of v0.1.435 or later. The boot log says which (`monster AI on: ...` / `monster AI off ...`). See `deploy/README.md`, "Monster AI (off by default)" |
| `-monster-strike-push` | `SRREVAMP_MONSTER_STRIKE_PUSH` | **default off**. On, a monster's counterattack is also sent to its whole zone, the attacker included, as `OpMonsterAttacked 0x007D`, after the attacker's `OpAttackResult`, so every player there sees the blow (round 541). Off, nothing is sent and the wire is what it was. Independent of `-monster-ai`. The env value is parsed like `-monster-ai`'s; anything else is off with a WARN. Needs a client release that carries round 540: v0.1.436 (round 542) does, and its `Release client` run is green (`gh run list`, 2026-09-24); an older one ignores the push, warning "unhandled opcode" once per connection. Its render-box live check passed in round 543. The boot log says which (`monster strike push on: ...` / `monster strike push off ...`). See `deploy/README.md`, "Monster strike push (off by default)" |
| `-monster-spawn-push` | `SRREVAMP_MONSTER_SPAWN_PUSH` | **default off**. On, a monster that has just appeared -- a roster respawn or a GM `/spawn` -- is sent to its whole zone at once as `OpMonsterSpawned 0x007E` (round 542): the monster list's own record, then the heading it hatched facing (`Nest_Hatch`'s `rand() / 32767 * 2pi`, rolled at the spawn; the monster AI starts from the same heading). Off, nothing is sent and the wire is what it was: a client finds the monster on its next monster list. Independent of `-monster-ai`. The env value is parsed like `-monster-ai`'s; anything else is off with a WARN. Needs the client release that carries round 540, v0.1.436, as `-monster-strike-push` does; an older one ignores the push, warning "unhandled opcode" once per connection. Its render-box live check has not been run yet. The boot log says which (`monster spawn push on: ...` / `monster spawn push off ...`). See `deploy/README.md`, "Monster spawn push (off by default)" |
| `-monster-battle` | `SRREVAMP_MONSTER_BATTLE` | **default off**. On, a struck monster fights on its own (round 546): it chases its attacker to its attack band at its run speed (`OpMonsterMoved` mode 1), swings on its attack skill's ReuseDelay with each blow pushed to the zone as `OpMonsterAttacked 0x007D` (immediate on entering BATTLE, then every ReuseDelay: 3000 ms for a Mangyang), gives up by distance (400 units, an own-design `_RefTactics` stand-in) and walks home, and the counterattack inside the attacker's `OpAttackResult` is no longer made. Off, the interim hold and the synchronous counter are what they were. Since round 553 the same flag carries the **aggro link**: a party member's first hit on a monster not yet fighting pulls in as many of the ten nearest other monsters (within its detection radius scaled by the level gap between it and the attacker) as the party has members within 1000 units of the attacker, each engaged by the chase and the swings; a solo hit links nothing, and nothing links with the flag off (`docs/protocol/monster_ai.md`, "The aggro link: the runtime (round 553)"). Since round 554 it also draws each swing among a species' attack skills (characterdata cols 83..92): Mangyang, Water Ghost slave, Water Ghost and Yeoha carry two, drawn by AI_AttackChance plus half the reach margin (`ai.PickSkill`), the band and the cooldown following the drawn skill -- a Yeoha can open with its 100-unit ATTACK03 from afar, and a Water Ghost's ATTACK02 lands no damage (a status skill srrevamp has no system for). Single-skill species are unchanged, and the flag-off counter still rolls the primary skill (`docs/protocol/monster_ai.md`, "The second attack skill: the runtime (round 554)"). **Forced off with a WARN** (`monster battle forced off`) unless `-monster-ai` and `-monster-strike-push` are both on: the chase runs in the AI tick, and without the push a player would lose HP to blows nobody is told about. The env value is parsed like `-monster-ai`'s; anything else is off with a WARN. Needs a client release that carries round 546 (an older one draws a blow on the player as the monster's swing alone). The boot log says which (`monster battle on: ...` / `monster battle off ...`). See `deploy/README.md`, "Monster battle (off by default)" |
| `-monster-aggro` | `SRREVAMP_MONSTER_AGGRO` | **default off**. On, monsters NOTICE players (round 552): a monster idle, wandering or, once its blackout has passed (the time to run its own radius: 4818 ms for a Mangyang), running home scans on its own timer -- every 1001-1500 ms, rolled once per spawn, the first scan at once -- for the nearest LIVING player within its acquisition radius, its collision radius + 100 units (the detection distance, an own-design stand-in for a server-database column: 104-111 units for the roster), and engages it exactly as a blow would, through `-monster-battle`'s chase and swings (`OpMonsterMoved` mode 1, `OpMonsterAttacked 0x007D`). A dead player is no candidate. Off, a monster fights only when struck and the wire is what it was. **Forced off with a WARN** (`monster aggro forced off`) unless `-monster-battle` is in effect (so `-monster-ai` and `-monster-strike-push` too) and `-player-dead-state` is on: a noticed player is engaged by the chase and the swings, and a monster that seeks players out kills ones who never struck it, who must then stay dead. The env value is parsed like `-monster-ai`'s; anything else is off with a WARN. Needs the client releases those two flags need (rounds 546 and 548). Its render-box live check: `docs/protocol/monster_ai.md`, "Target acquisition: the runtime (round 552)". The boot log says which (`monster aggro on: ...` / `monster aggro off ...`). See `deploy/README.md`, "Monster aggro (off by default)" |
| `-single-frame` | `SRREVAMP_SINGLE_FRAME` | **default off**, and the kill switch. On, the whole world is ONE coordinate frame (round 571): every zone the server knows a frame for (the named towns and any `x/y` region) is named in Jangan's frame -- `FrameRegion` "97/168" on `OpEnterWorldResult` and `OpChangeZoneResult` -- and kept in ONE broadcast bucket (`world`), every roster monster with it (each npcpos row converted against 97/168, an own-design anchor moved into it); a zone change, and so a GM `/goto <town>`, lands at the middle of the town's centre region named in that frame (Donwhang at `ToWorld(102, 153, 960, 960, 97, 168)`), not at (0, 0, 0). So a player who walks from Jangan toward Donwhang meets Donwhang's monsters and every other player. The zone label stays the client's grid-centre hint; a change to a framed label is always a warp (never "already in that zone"), and the others in the world see the mover leave and re-enter. One bucket means no spatial filter: moves, local chat and the monster and ground-item lists (413 monsters with `-npcpos-csv`) reach the whole world, while a range rule such as trade's 320 units now compares positions in the one frame. A label with no frame keeps its own bucket and the old wire. Off, every zone keeps its own frame and bucket and the wire is what it was. OWN DESIGN, disclosed (`worldmap.WorldOrigin`). The env value is parsed like `-monster-ai`'s; anything else is off with a WARN. Needs a client release that carries rounds 569 to 571 (round 571's client finds the grid's corner when a centre region's terrain fails to load; `deploy/README.md`'s condition 1). The boot log says which (`single frame on: origin 97/168 ...` / `single frame off ...`). See `deploy/README.md`, "Single world frame (off by default)" |
| `-persist-position` | `SRREVAMP_PERSIST_POSITION` | **default off**, and the kill switch. On, a character logs back in where it left off (round 573): its zone label, the frame region its coordinates are in and its position are saved on its row (`latest_zone`, `latest_frame`, `pos_x`/`pos_y`/`pos_z`, the engine's `_CHAR.LatestRegion`/`PosX`/`PosY`/`PosZ` in srrevamp's shape) on a disconnect, on each zone change, at most every 30 s while it walks (own design) and for everyone still in the world when the server stops; the next `OpEnterWorldResult` answers that label, the label's bucket and frame of the day, and the saved point named in that frame (`worldmap.Rebase`; a height from another frame becomes 0), with a trailing `Restored` byte 0x01 after `FrameRegion`. A character with nothing saved, or whose saved frame cannot be named in today's, enters at the spawn. Off, nothing is saved or read and the wire is what it was. The env value is parsed like `-monster-ai`'s; anything else is off with a WARN. Needs a client release that carries round 573: an older one ignores the byte and moves a restored Jangan entry on to Jangan's landing spot, as it always has. The boot log says which (`persist position on: ...` / `persist position off ...`). See `deploy/README.md`, "Saved position (off by default)" |
| `-player-dead-state` | `SRREVAMP_PLAYER_DEAD_STATE` | **default off**. On, a player a monster kills STAYS DEAD (round 549): life state 2 at HP 0 -- the kill's `OpAttackResult` and `OpMonsterAttacked` carry HP 0 instead of the respawned 40 % -- with its potion queue emptied, its moves neither stored nor relayed, its attacks, casts, items, pick-ups, duel blows, trade requests, zone changes, GM `/tp`/`/goto` and guild founding / level-ups refused, and no monster's target, until it sends `OpRevive 0x0028` (answered by `OpReviveResult 0x0029`: revived where it lies, HP at 1 + 40 % of the maximum (truncated) and MP at 40 %, the retail resurrect handler's own arithmetic (round 550) -- grounded for a max level of 10 or under, a disclosed stand-in above it, where retail returns the character to its appointed teleport) or 30 s pass (the auto-revive fallback, own design). Off, a kill respawns the player at once and the wire is what it was. Independent of the monster flags: it covers the synchronous counter and the AI's own swings alike. The env value is parsed like `-monster-ai`'s; anything else is off with a WARN. Needs a client release that carries round 548 (the dead pose and the Revive button); an older client shows HP 0 with no button and is freed by the fallback alone. Its render-box live check has not been run yet. The boot log says which (`player dead state on: ...` / `player dead state off ...`). See `deploy/README.md`, "Player dead state (off by default)" |

At boot the server logs what reference data its database holds
(`reference data in PostgreSQL items= skills= monsterDrops= dropGroupEntries=`)
and **warns when it has no items** — that state is what made every hit deal 1
and no kill pay EXP on the public server until 2026-09-19. Env-only settings
are the QA accelerants, which are never for real play
(`SRREVAMP_DURABILITY_LOSS_ALWAYS`), and the monster AI's trace
(`SRREVAMP_AI_TRACE`: every state change, leg, strike and release, and a keep-up
that ends out of reach -- several lines a second in Jangan, so only for a check). The GM console's account list is the
`-gm-accounts` flag above (env `SRREVAMP_GM_ACCOUNTS`); the commands a tester
and a GM get are in `docs/DEBUG_TOOLS.md`.

## Reference data

The server reads no game text tables directly. The operator generates CSVs from
their own `Media.pk2` and either passes them on the command line (in-memory) or
imports them into PostgreSQL:

- `cmd/export-refdata` — itemdata / skilldata text tables → `items.csv`, `skills.csv`
  (read in the client's **index order**, not glob order: ids collide across parts);
  `-mode npcpos` → `npcpos.csv`; `-mode teleport -out <dir>` → the three teleport CSVs.
- `cmd/export-leveldata` — `leveldata.txt` → `leveldata.csv` (the EXP curve).
- `cmd/import-refdata` — loads items, skills and, when an operator has them, the
  drop tables (`-drops-csv`, `-drop-groups-csv`) into PostgreSQL. The drop tables
  live only in the original shard database and are absent from every client
  archive; until an operator supplies them, loot content is a disclosed placeholder.

The full recipe, as actually run on the public server, is `deploy/README.md`.

## Layout

`internal/` is one package per system; the ones that carry recovered rules cite
their source in the code (`combat`, `durability`, `berserk`, `leveldata`,
`skillparam`, `character`, `equipment`, `grounditem`, `repair`, `rates`,
`storage` -- the warehouse is the account's, with a one-time boot migration
from the older per-character table).
`session` holds the wire handlers (our own protocol; opcodes and payloads are
documented next to the handlers and in `docs/protocol/`), `gateway` the TCP
layer, `world` the zone hub, `persistence` the recovered model of the original
database, and `systems` the test that keeps `docs/SYSTEMS.md` honest.

## Tests

`go test -p 1 ./...` from this directory. Twelve packages' tests use a local
PostgreSQL test database (`SRREVAMP_TEST_POSTGRES_DSN`, default
`postgres://postgres:postgres@localhost:5432/srrevamp_test?sslmode=disable`);
`internal/testdb` serialises test *processes* on it with an advisory file lock,
so parallel suite runs from several checkouts no longer clobber each other's
rows (two runs both pass; the second waits). The `systems` and `refdata`
packages guard the documentation: `docs/SYSTEMS.md`'s rows, this README, and
`docs/protocol/recovered_names.tsv`.
